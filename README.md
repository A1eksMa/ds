# ds

**Встраиваемый движок хранения историзированных данных из разнородных источников** и набор
инструментов инженера данных для работы с ним.

`ds` принимает периодические плоские выгрузки из систем-источников (CRM, ERP, отчёты), хранит
все изменения как неизменяемый журнал с атрибуцией «кто, что, когда сообщил» и позволяет
восстановить состояние данных на любой момент времени.

Это **нижний слой** (система записи): семантическая обработка, разрешение противоречий между
источниками и пользовательские интерфейсы — задача вышестоящего слоя и в этот репозиторий
не входят. Подробнее — [`docs/explanation/scope-and-non-goals.md`](docs/explanation/scope-and-non-goals.md).

## Статус

Альфа (`0.9.0a1`). Работает: загрузка колоночного JSON (`ds load`, либо `ds upload` — то же
самое, но отказывает целиком, если файл несёт хоть один необъявленный показатель или значение
не по объявленному типу) с автоопределением операции и декларативным инвентарём показателей в
`source.json` (`type`/`archive`/`publish` — см.
[`docs/reference/config-format.md`](docs/reference/config-format.md)), который `ds update`
умеет синхронизировать с реальным состоянием БД; выгрузка состояния источника на дату (`ds
get`, свёртка Level 1, пресеты, инкрементальный кэш `--cache` — не пересчитывает всю историю
заново, если с прошлого вызова источник не менялся структурно, см.
[ADR-0010](docs/decisions/0010-incremental-fold-cache.md)); удаление, архивирование,
восстановление из архива и дедупликация транзакций (`ds delete`/`ds archive`/`ds unarchive`/
`ds compact`) на общем селекторе — источник, показатели, ключи явным списком или по условию на
текущее значение другого показателя (`--where`), конкретные записи по `cnt`, диапазоны
бизнес-времени и времени загрузки; переименование показателя и/или перенос его истории в
другой источник (`ds mv`, с автоматическим слиянием, если показатель назначения уже накопил
часть истории за переходный период); event-sourcing схема, партиционирование основной/
архивной таблиц, два адаптера хранилища.

Пока не реализовано (в scope, см. [`docs/roadmap/`](docs/roadmap/)): split и слияние
источников целиком, чистка дублей в `ids`/`vals`, автоматическое архивирование по правилу,
миграции, дальнейшая оптимизация (чистка осиротевших записей пулов, `VACUUM`).

## Быстрый старт

```bash
pip install -e .

mkdir -p sources/CRM
echo '{"name": "CRM", "key_label": "customer_id"}' > sources/CRM/source.json

cat > batch.json <<'JSON'
{ "customer_id": ["101","102"], "email": ["a@ex.com","b@ex.com"] }
JSON

ds --db data.db load sources/CRM batch.json --dt 1704067200
# loaded 2 transaction(s)
```

Полный сценарий — [`docs/guides/getting-started.md`](docs/guides/getting-started.md).
Запускаемые примеры — [`examples/`](examples/).
