# Управление сущностями схемы (merge / split / delete / rename)

> **Статус в коде:** rename/merge для `lbs` — реализовано (`ds mv`, см.
> [`../reference/cli.md#ds-mv`](../reference/cli.md#ds-mv)). Остальное (merge `srcs`,
> merge `ids`/`vals`, split любой сущности) — не реализовано; здесь для них — постановка
> задачи и открытый вопрос. План — [`../roadmap/entity-curation.md`](../roadmap/entity-curation.md).

## Задача

Структура данных со временем «дрейфует»:

- Показатель называли `Производитель`, с какого-то момента источник стал присылать его как
  `Изготовитель`. Это **одна и та же** сущность, но в `lbs` теперь две записи с разными
  `lb_id` (метки специфичны для источника — [`source-specific-labels.md`](source-specific-labels.md)).
  Решено — `ds mv`, см. ниже.
- Два потока данных оказались одним источником (или один источник разделили на два).
- В пул `ids` попал мусор / дубли из-за разного форматирования ключа.

Нужен инструментарий инженера, чтобы **привести схему в порядок**: слить, разделить,
переименовать, удалить записи пулов `srcs` / `lbs` / `ids` / `vals`.

| Операция | Смысл |
|---|---|
| **merge** | два `lb_id` (или `src_id`, `id_id`, `val_id`) — на самом деле одно; свести все транзакции к одному, второй списать |
| **split** | один `lb_id` конфлатил два разных понятия; разбить транзакции по предикату на два |
| **rename** | сменить `name` / `description` без пересборки ссылок |
| **delete** | убрать запись пула и связанные транзакции (сейчас FK = `RESTRICT` — нужен явный порядок) |

## Это администрирование хранилища, а не семантика

Граница чёткая:

- **Решение** «это одна и та же сущность» принимает человек или слой обработки. Ядро его
  **не** принимает и семантику не анализирует.
- **Исполнение** структурной операции (переписать журнал / ссылки) — задача ядра.

Поэтому merge/split — **в scope ядра** (см. [`scope-and-non-goals.md`](scope-and-non-goals.md)),
а вот определение кандидатов на слияние по смыслу — нет. Открытый подвопрос: даёт ли ядро
*механическую* подсказку (одноимённые метки в непересекающихся диапазонах `dt`; источники с
похожими именами) или получает только явную инструкцию «слей X и Y».

## Открытый вопрос: переписывание журнала vs событие

merge/split конфликтуют с инвариантом «журнал неизменяем» (см. [`event-sourcing.md`](event-sourcing.md)).
Два подхода:

| Подход | Плюсы | Минусы |
|---|---|---|
| **Переписать журнал** (`UPDATE transactions SET lb = :keep WHERE lb = :drop`, затем удалить строку пула) — админ-миграция вне event-модели | чистый журнал, один `lb_id` на понятие, читателям ничего знать не нужно | нарушает append-only; нужна аккуратность с архивом и FK `RESTRICT` |
| **Слой алиасов** (`lbs.merged_into`, резолв на чтении) или отдельные события слияния | неизменяемость сохранена, обратимо | сложность у каждого читателя; «две метки» никуда не делись |

Для `lbs` решено — вариант «переписать журнал» (`ds mv`); для остального решение не
принято — [`../decisions/0009-entity-curation-rewrite-vs-events.md`](../decisions/0009-entity-curation-rewrite-vs-events.md).
