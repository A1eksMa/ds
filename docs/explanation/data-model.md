# Модель данных: четвёрки `src–lb–id–val`

## Суть

Любой факт в `ds` — это четвёрка:

```
(source, label, id) → value
 источник  показа-   объект   значение
           тель
```

Плюс служебные поля транзакции: `act`, `dt`, `created_at`, `cnt`, `p`.

Пример: строка «у клиента `101` из `CRM` поле `email` равно `alice@example.com`» —
это `(CRM, email, 101) → alice@example.com`.

## Это EAV (Entity–Attribute–Value)

Схема — «узкая таблица»: не «одна колонка на показатель», а «одна строка на ячейку».
Составной ключ сущности — `(src, id)`, атрибут — `lb`, значение — `val`.

**Почему так, а не широкая таблица с колонкой на показатель:**

- Источники приносят **произвольные и меняющиеся** наборы показателей. Широкая таблица
  требовала бы `ALTER TABLE` на каждый новый столбец в любой выгрузке.
- Данные **разреженные**: у объекта заполнена малая часть возможных показателей. Широкая
  таблица была бы забита `NULL`.
- Нужна **пооперационная история на каждую ячейку** (кто и когда менял именно `email`
  клиента `101`), а не на строку целиком.

## «Схема гибкая, но данные структурированы»

`ds` иногда называют «NoSQL по духу», и это про одно конкретное свойство: **состав
показателей не объявляется заранее**. Любая колонка в загружаемом файле принимается и
регистрируется как метка на лету.

Но сама структура — жёсткая: всё сводится к четвёрке фиксированной формы, все значения
хранятся как строки (`TEXT`), типизация и разбор — забота вышестоящего слоя. Это не
«неструктурированные данные», а **фиксированная схема с гибким составом атрибутов** и
schema-on-read для значения.

## Что где хранится

| Часть четвёрки | Пул | В журнале |
|---|---|---|
| `source` | `srcs` (+ метаданные: `p`, `description`, `key_label`) | `transactions.src` — INTEGER |
| `label` | `lbs` (+ `p`, `description`, `src_id`) | `transactions.lb` — INTEGER |
| `id` | `ids` (только `value`) | `transactions.id` — INTEGER |
| `value` | `vals` (только `value`) | `transactions.val` — INTEGER, `NULL`/`0` = удаление |

Почему строки вынесены в пулы — [`dictionary-encoding.md`](dictionary-encoding.md).
Полная схема с DDL — [`../reference/database-schema.md`](../reference/database-schema.md).

## Границы модели

- `id` уникален в пределах **пула `ids` целиком**, а не в пределах источника. Один и тот же
  `customer_id = "101"` из CRM и `"101"` из ERP — это один `id_id`. Разводит их `src` в
  четвёрке.
- `label`, наоборот, **не** глобален: `email` в CRM и `email` в ERP — разные `lb_id`.
  См. [`source-specific-labels.md`](source-specific-labels.md).
- Сведе́ние одноимённых показателей/объектов между источниками в модели ядра **не выражено** —
  это делает слой обработки.
