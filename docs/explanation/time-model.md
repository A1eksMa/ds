# Три оси времени: `dt`, `created_at`, `cnt`

У каждой транзакции три разных временны́х поля. Они не взаимозаменяемы.

| Поле | Смысл | Кто задаёт | Пример вопроса, на который отвечает |
|---|---|---|---|
| **`dt`** | бизнес-время: «с какого момента данные актуальны» | вызывающая сторона (`--dt`), может быть любым, в т.ч. в прошлом | «Каким был профиль клиента на 11 октября?» |
| **`created_at`** | физическое время: «когда запись реально попала в БД» | хранилище, один раз при вставке | «Почему сегодняшний отчёт отличается от вчерашнего, хотя период тот же?» (данные долетели с задержкой) |
| **`cnt`** | порядок вставки в хранилище, монотонный счётчик | хранилище (`AUTOINCREMENT`) | «Какая из двух записей с одинаковым `dt` пришла позже?» (финальный tie-break) |

## Битемпоральность

`dt` и `created_at` — это две независимые оси: **время предметной области** и **время
системы**. Классическая битемпоральная модель (valid time / transaction time). Пример, где
они расходятся:

```
Источник сформировал выгрузку за 2024-01-01, но прислал её только 2024-01-05.
  dt         = 2024-01-01  (данные актуальны на эту дату)
  created_at = 2024-01-05  (в этот день их физически загрузили)
```

Срез «на 2024-01-02» построенный 2024-01-03 этих данных **не увидит**, а построенный
2024-01-06 — увидит, хотя `dt` тот же. `created_at` объясняет, почему один и тот же по
параметрам запрос дал разные ответы в разные дни.

## «Машина времени»

Поскольку журнал append-only (см. [`event-sourcing.md`](event-sourcing.md)), состояние можно
собрать на любой момент `T`: берутся транзакции с `dt <= T`, сворачиваются в состояние
(см. [`single-source-fold.md`](single-source-fold.md)). Обновления с `dt > T` игнорируются.

## Почему `cnt`, а не `created_at`, — финальный tie-break

При пакетной загрузке `created_at` может совпасть у многих строк (одна и та же доля секунды).
`cnt` — единственное поле, гарантированно не повторяющееся (`INTEGER PRIMARY KEY
AUTOINCREMENT`). Поэтому когда совпали и `dt`, и веса, «победителя» выбирают по большему
`cnt`. Подробнее о порядке свёртки — [`single-source-fold.md`](single-source-fold.md) и
[`../decisions/0006-fold-order-dt-cnt.md`](../decisions/0006-fold-order-dt-cnt.md).

## Практическое применение: отбор для `ds delete`/`ds archive`

Ровно эта разница между осями — причина, по которой у `ds delete`/`ds archive` два независимых
диапазона, а не один: `--dt-from`/`--dt-until` отбирает по периоду, к которому относятся
данные («убрать всё за январь»), `--created-from`/`--created-until` — по тому, когда данные
физически загружены («убрать всё, что подгрузили конкретно во вторник», независимо от того, к
какому периоду эти записи относятся). См.
[`../reference/cli.md#ds-delete--ds-archive`](../reference/cli.md#ds-delete--ds-archive).

## Замечание о воспроизводимости

`dt` и `cnt` воспроизводятся при повторном прогоне одних и тех же загрузок; `created_at` —
нет, это реальное время выполнения.
