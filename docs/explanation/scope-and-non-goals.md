# Границы ядра: что входит и что нет

Репозиторий намеренно заморожен на слое **ядра-хранилища**. Это решение зафиксировано в
[`../decisions/0007-scope-freeze-storage-core.md`](../decisions/0007-scope-freeze-storage-core.md).

## Входит в ядро

| Область | Что именно | Статус |
|---|---|---|
| **Приём данных** | загрузка колоночного JSON, валидация, снапшот-диф → авто-`act` (`POST`/`PATCH`/`DELETE`) | реализовано (`ds load`) |
| **Историзация** | неизменяемый битемпоральный журнал транзакций, партиционирование основной/архивной таблицы | реализовано |
| **Выдача состояния** | состояние **одного источника** на заданный момент времени по запросу внешней системы (Level 1: свёртка last-write-wins по `dt`/`cnt`) | реализовано (`ds get`, см. [`../reference/get-output-format.md`](../reference/get-output-format.md)); Level 2 — вне ядра |
| **Жизненный цикл** | архивирование («мягкое» удаление), физическое удаление, retention | частично: на уровне `StoragePort` (`txn_archive`, `txn_delete`), не выведено в CLI → [roadmap](../roadmap/lifecycle-cli.md) |
| **Управление сущностями схемы** | merge / split / delete / rename над `srcs`, `lbs`, `ids`, `vals` (пример: показатель переименовали «Производитель» → «Изготовитель» — два `lb_id`, надо свести в один) | [запланировано](../roadmap/entity-curation.md) |
| **Миграции схемы** | инструменты миграции при изменении структуры самого ядра | [запланировано](../roadmap/schema-migration.md) |
| **Оптимизация** | индексы, `VACUUM`, дедупликация, ускорение поиска/сортировки | [запланировано](../roadmap/optimization.md) |

## Не входит — вынесено в вышестоящий слой (отдельный проект)

| Что | Почему не здесь |
|---|---|
| **Семантический маппинг** — «`CRM.Contract_Number` и `ERP.Agreement_ID` — это одна сущность» | Решение о смысловом тождестве принимает человек / слой обработки. Ядро хранит источники как есть и умеет только выполнить явную структурную операцию (merge), но не *решить*, что её надо сделать. |
| **Разрешение коллизий между источниками (Level 2)** — выбор значения по `p_source × p_label × p_record` | Это политика поверх данных, а не свойство хранилища. Веса `p` в схеме есть (см. [`trust-weights.md`](trust-weights.md)), но их применение — наверху. |
| **Управление приоритетами и состояниями пользователем, любой UI** | Ядро — CLI-инструмент инженера, не продукт для конечного пользователя. |
| **Доменная логика, BI-аналитика, подготовка данных** | Своя у каждой предметной области. Живёт в «обвесе» вне репозитория. |

## Что это значит для документации

- Всё из `docs/proposals/` про Entity Manager, двухуровневый движок, семантику — переехало в
  [`../attic/`](../attic/) с пометкой «не строим по этому».
- `reference/` описывает только то, что уже в коде.
- `roadmap/` — только то, что **сядет в ядро** (список выше), а не весь исходный замысел.
