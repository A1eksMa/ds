# 0010. Инкрементальная свёртка: приватный кэш `ds get --cache`, а не алгоритм в `ds-loader`

- **Статус:** Принято, реализовано (0.10.0a1)
- **Дата:** 2026-10-03

## Контекст

`ds get` каждый раз пересчитывает срез с нуля: `build_source` берёт всю историю источника
по условию `dt <= as_of` (`StoragePort.txn_query`) и сворачивает её в Python (Level 1,
[ADR-0006](0006-fold-order-dt-cnt.md)) — O(всей активной истории источника), независимо от
того, сколько в ней реально изменилось с прошлого вызова. `ds-loader` (`publish_stage`)
дёргает `ds get` на каждый тик опроса; при росте базы это стало узким местом сборки
выгрузки для `ds-webui`, отдельным от уже решённой проблемы тормозов самой вьюшки (см.
project memory: «известное ограничение масштаба» — решено сужением рабочего множества,
не тут).

Полная пересборка — единственная гарантия корректности (нет версии схемы отдельно от кода,
[ADR-0008](0008-no-separate-schema-versioning.md)), и это нужно сохранить как безопасный
fallback. Вопрос — как получить быстрый путь для «ничего структурного не произошло, просто
добавились записи», не теряя эту гарантию.

## Где живёт состояние и алгоритм мержа

Рассматривались два варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Состояние и мерж — в `ds-loader`**: он хранит прошлый опубликованный payload + `cnt`, сам реализует формулу победителя `(dt, cnt)` поверх нового примитива `ds dump` (сырые транзакции с `--from-cnt`). | `ds` не меняется вообще. | Дублирует формулу свёртки ([ADR-0006](0006-fold-order-dt-cnt.md)) во внешнем репозитории — рассинхронизируется при любом будущем изменении порядка свёртки. Опубликованный payload (`{meta, data}`) хранит только резолвленные значения, не `(dt, cnt)` победителя — **непригоден** как вход для мержа без доп. формата. |
| **Состояние — в `ds-loader`, мерж — в `ds`** (принято): `ds-loader` только хранит opaque-файл и передаёт его обратно через `ds get --cache <path>`; весь мерж — внутри `ds`. | Формула свёртки остаётся в одном месте. `ds-loader` не знает о `struct_version`/`cnt`/формате кэша — просто таскает файл туда-обратно. | `ds` обзаводится файловым side-effect-ом (раньше работал только с БД) — но он опционален (`--cache`) и по шаблону, уже заданному `--preset`/`--out`. |

## Решение

1. **`srcs.struct_version`** — счётчик, инкрементируемый `txn_delete`/`txn_archive`/
   `txn_unarchive`/`lb_merge` (а значит и `ds compact`, который вызывает их же), и только
   ими — **не** `txn_insert`/`ds load`. Это единственный сигнал «источник менялся
   структурно», без диффа всей свёртки.
2. **`ds get --cache <path>`** — если файл есть и для запрошенного источника совпадают
   `struct_version`, набор показателей и `include_archive`, а `as_of` не уменьшился —
   берётся прошлый результат свёртки как затравка и доливаются только новые транзакции
   (`txn_query(..., from_cnt=...)`). Любое расхождение (другая версия, другие показатели,
   откат `as_of` назад, файла нет/битый) — тихий fallback на полную пересборку, как раньше.
3. **Формат кэша — приватный контракт `ds`**, не публичный `{meta, data}`: он хранит
   `(dt, cnt, val_id)` победителя на каждую пару `(показатель, id)`, а не только значение —
   это и есть то, что умеет мержиться формулой из [ADR-0006](0006-fold-order-dt-cnt.md).
   Файл не нужно стабилизировать как внешний контракт (в отличие от схемы БД,
   [ADR-0008](0008-no-separate-schema-versioning.md)) — это deja vu "кэш", можно менять
   формат в будущих версиях `ds` без миграций, просто инвалидируя старый файл.
4. **Будущие бизнес-даты (`dt` в будущем относительно `as_of`)** обрабатываются отдельным
   doc-fix: транзакция может получить `cnt` раньше, чем её `dt` войдёт в срез (запланированное
   изменение), и будет исключена из фолда по `until_dt`, но не по `from_cnt` — чистый
   cnt-водяной знак навсегда бы её потерял. Поэтому второй, более узкий запрос на каждый
   инкрементальный проход — `from_dt=<прошлый as_of>, until_dt=<новый as_of>` — подбирает
   такие «отложенные» строки. Оба запроса мержатся в одну и ту же свёртку (мерж
   идемпотентен/коммутативен по построению, см. [ADR-0006](0006-fold-order-dt-cnt.md)),
   так что пересечение результатов безвредно.
5. **Побочно найденное и тоже исправленное**: даже с кэшем на свёртку, сборка `data` всё
   равно резолвила `id_get`/`val_get` **по одному** round-trip'у на ячейку — O(всех текущих
   строк) независимо от кэша, и на 60k строк это доминировало над самой свёрткой (~5.4s из
   ~9s в замере). Добавлены `StoragePort.id_get_many`/`val_get_many` (один запрос `IN (...)`,
   чанками) — выигрыш общий для обоих путей (с кэшем и без), не только для инкрементального.

## Последствия

- `ds get`'s итоговый JSON (`{meta, data}`) не меняется ни байтом — `--cache` только решает,
  *как* он посчитан, не *что* в нём.
- `ds-loader` меняется минимально: `publish_stage` просто всегда передаёт
  `--cache <publish_cache_path>` в `ds get`, без собственной логики инвалидации.
- Кэш-файл не нужно бэкапить/версионировать вместе с БД: потеря или ручное удаление файла —
  не ошибка, а просто следующий вызов будет на один раз медленнее (полная пересборка).
- Split/слияние источников/дедуп `ids`/`vals` ([ADR-0009](0009-entity-curation-rewrite-vs-events.md))
  в будущем тоже обязаны бампать `struct_version` затронутых источников, если/когда будут
  реализованы — иначе `--cache` молча отдаст устаревшие данные после такой операции.
