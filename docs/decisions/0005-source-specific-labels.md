# 0005. Метки специфичны для источника

- **Статус:** Принято, реализовано (0.5.0a1)
- **Дата:** 2025-08 (прежний `TODO.md`, п. 4)

## Контекст

Раньше `lbs` был глобальным пулом по имени: две метки с одинаковым именем из разных источников
писались как одна запись. Это риск коллизий: одноимённые показатели разных систем могут
означать разное, а разноимённые — одно и то же.

## Решение

`lbs` уникальна по паре **`(src_id, name)`**; `lbs.src_id INTEGER NOT NULL`. В домене — поле
`Lb.src: SrcId`. `StoragePort.lb_intern(name)` → `lb_intern(name, src_id)`.

Метка существует только в контексте источника. Совпадение имени — не гарантия совпадения
сущности, и наоборот.

## Альтернативы

- Оставить общий пул + таблица override'ов `src_label_overrides(src_id, lb_id, p_override, ...)`
  — сохраняет глобальные метки, позволяет точечно переопределять вес/описание. Отклонено: не
  соответствует модели «метка живёт в контексте источника» и не решает исходную коллизию имён.

## Последствия

- **Циклическая зависимость `Src` ↔ `Lb`** (`srcs.key_label` → `lbs`, `lbs.src_id` → `srcs`).
  Решено бутстрапом: `Src` создаётся с `key_label = NULL` → интернируется ключевая метка с
  `src_id` → `src_set_key_label()`. Поэтому `srcs.key_label` — nullable,
  `Src.key_label: Optional[LbId]`.
- Breaking change контракта порта: затронуты оба адаптера, `service/load.py`, весь периметр
  тестов loader/adapters/mappers.
- **Level 2 дороже:** будущий слой обработки не может сопоставлять метки разных источников по
  `lb_id`/имени — нужен отдельный явный слой соответствия (в ядре его нет). Механическую часть
  (свести два `lb_id`) закрывает [`../roadmap/entity-curation.md`](../roadmap/entity-curation.md).
