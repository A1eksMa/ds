# 0004. `created_at` — поле в `transactions`, без отдельного класса `Cnt`

- **Статус:** Принято, реализовано (0.5.0a1)
- **Дата:** 2025-08 (обсуждение в прежнем `TODO.md`, п. 2)

## Контекст

Нужна техническая отметка «когда запись физически попала в БД» — отдельно от `dt` (бизнес-время,
когда факт произошёл) и `cnt` (порядок вставки). Конкретный потребитель: инженерам нужно
объяснять, почему сегодняшний отчёт отличается от вчерашнего, когда данные идут в систему с
задержкой в несколько дней. `created_at` = «когда данные долетели».

Раньше `sqlite_adapter` писал `created_at` только в таблицу `cnts` (`julianday('now')`), и
ни один `SELECT` его не возвращал — поле было мёртвым.

## Решение

Поле `created_at REAL NOT NULL` — **прямо в `transactions`** (и `transactions_archive`), плюс
в доменные `Transaction`/`TransactionRecord`. Отдельная сущность/класс `Cnt(cnt_id, created_at)`
**не** вводится. Значение генерируется один раз на стороне Python через `ClockPort` (не
читается обратно из БД через `julianday('now')`).

## Альтернативы

- Отдельный класс `Cnt` + JOIN `cnts` на каждом чтении транзакций — соответствует нормализации
  (`cnts` уже отдельная таблица), но `cnt_id` и `created_at` связаны 1:1, и `created_at`
  никогда не запрашивается в отрыве от транзакции. Лишний JOIN на горячем пути без выигрыша в
  инкапсуляции. Отклонено.

## Последствия

- Небольшая денормализация: таблица транзакций тяжелее на одно поле, зато нет JOIN на чтении.
- `Transaction`/`TransactionRecord` — frozen dataclass, используется по всей кодовой базе и в
  юнит-тестах, собирающих объекты вручную; все места конструирования обновлены.
- `InMemoryAdapter` теперь тоже генерирует `created_at` (раньше там был только счётчик).
- Появилась третья ось времени — см. [`../explanation/time-model.md`](../explanation/time-model.md).
