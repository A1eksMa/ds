# 0002. Хранение как неизменяемый журнал транзакций

- **Статус:** Принято
- **Дата:** 2025-11-01

## Контекст

Данные об одних и тех же объектах приходят из разных источников периодическими плоскими
срезами, с задержками и противоречиями. Нужны: полная история изменений, восстановление
состояния на любой прошлый момент, отсутствие потери данных при обновлении, прозрачное
происхождение (data lineage).

## Решение

Event sourcing: каждое изменение — отдельная строка в append-only журнале `transactions`.
«Текущее значение» не хранится, а вычисляется свёрткой журнала до нужного момента
(см. [`../explanation/single-source-fold.md`](../explanation/single-source-fold.md)).
Партиционирование на `transactions` / `transactions_archive` для управления объёмом.

## Альтернативы

- Обновление «на месте» (одна строка на `(src, lb, id)`, `UPDATE`) — теряет историю, не даёт
  «машину времени», плохо работает с задержанными источниками.
- Хранить и журнал, и материализованное состояние синхронно — усложняет запись; решено
  считать состояние на лету, а оптимизацию (снэпшоты) отложить.

## Последствия

- Чтение — это вычисление; отсюда идея снэпшотов/чекпоинтов (таблица `state`), пока не
  реализованная — [`../roadmap/state-retrieval.md`](../roadmap/state-retrieval.md).
- Журнал только растёт → нужны архивирование и физическое удаление
  ([`../roadmap/lifecycle-cli.md`](../roadmap/lifecycle-cli.md)).
- Загрузка не идемпотентна: тот же файл дважды → два комплекта транзакций.
- Операции merge/split над сущностями конфликтуют с неизменяемостью — [ADR-0009](0009-entity-curation-rewrite-vs-events.md).
