# 0006. Свёртка Level 1 — по `(dt, cnt)`

- **Статус:** Принято, реализовано (`src/service/get.py :: fold_source`; было снято в 0.5.0a1, переписано заново)
- **Дата:** 2025-08 (прежний `TODO.md`, п. 3)

## Контекст

В 0.3.0a1 `fold_state` определял победителя по `cnt` (порядок вставки), а не по `dt`
(бизнес-время). Это было осознанное решение (`cnt` системный, не искажается источником), но
оно затирало более новые по бизнесу данные более старыми, если те пришли в БД позже
(задержка источника).

Возник вопрос: не довериться ли `dt`? Контраргумент: `dt` — внешний вход, один неверный
timestamp (баг источника, часовые пояса) навсегда «выигрывает».

Контраргумент снят: доверие в модели фреймворка — **составное** (`dt` × вес `p`), а не
бинарная проверка правдоподобия `dt`. «Можно ли доверять данным» решается весом источника, а
не подменой `dt` на `cnt`.

## Решение

Трёхуровневое правило разрешения коллизий:

1. **Внутри источника (Level 1)** — приоритет по `dt`. Ключ сортировки — `(dt, cnt)`.
2. **Между источниками (Level 2)** — приоритет по весам `p`/`p_total`. **Вне ядра.**
3. **Финальный tie-break** (совпали `dt` и `p`) — по `cnt`, берём самый свежий. **Не** по
   `created_at`: при батч-загрузке `created_at` может совпасть, а `cnt` (PK AUTOINCREMENT) —
   нет.

## Последствия

- Ключ сортировки в свёртке — `(dt, cnt)`, а не `dt` и не `cnt` по отдельности.
- При реализации: развернуть тесты `test_fold_state_winner_decided_by_cnt_not_dt` и
  соседние; добавить тест «равный `dt` → побеждает больший `cnt`»; переписать docstring
  `fold_state`.
- Закрывает **только Level 1**. Level 2 (приоритет по `p` между источниками) — вне ядра.
- Целевая модель отражена в [`../explanation/single-source-fold.md`](../explanation/single-source-fold.md);
  формат выгрузки — [`../reference/get-output-format.md`](../reference/get-output-format.md).
