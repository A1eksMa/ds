# 0009. merge/split сущностей: переписывать журнал или моделировать событиями?

- **Статус:** Частично решено — вариант **A** принят и реализован для rename/merge одной
  метки (`ds mv`, `StoragePort.lb_merge`, см. [`../reference/cli.md#ds-mv`](../reference/cli.md#ds-mv)).
  Split, слияние источников целиком и чистка дублей в `ids`/`vals` остаются открытыми —
  см. [`../roadmap/entity-curation.md`](../roadmap/entity-curation.md).
- **Дата:** 2026-08-29 (открыто) / 2026-10-02 (решено для rename/merge `lbs`)

## Контекст

Ядру нужен инструментарий управления сущностями схемы: свести две метки в одну (переименование
показателя во времени: «Производитель» → «Изготовитель»), разделить конфлатившую метку, слить
источники, почистить дубли в `ids` (см. [`../explanation/entity-curation.md`](../explanation/entity-curation.md),
[`../roadmap/entity-curation.md`](../roadmap/entity-curation.md)).

Эти операции конфликтуют с инвариантом «журнал неизменяем» ([ADR-0002](0002-event-sourcing-journal.md)).

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Переписать журнал** — `UPDATE transactions SET lb = :keep WHERE lb = :drop`, затем удалить строку пула. Трактуется как админ-миграция вне event-модели. | Чистый журнал; один `lb_id` на понятие; читателям (в т.ч. верхнему слою) ничего знать не нужно. | Нарушает append-only; нужна аккуратность с `transactions_archive` и FK `RESTRICT`; необратимо без бэкапа. |
| **B. Слой алиасов** — `lbs.merged_into` (или таблица соответствий), резолв на чтении. | Неизменяемость сохранена; обратимо. | Сложность у каждого читателя; «две метки» физически остаются; усложняет все выборки и будущий `ds get`. |
| **C. Отдельные события слияния** в самом журнале (спец. `act`). | В духе event sourcing. | Свёртка усложняется; неясно, как это выглядит для внешнего потребителя состояния. |

## Открытые подвопросы

- Ищет ли ядро **кандидатов** на merge механически (одноимённые метки в непересекающихся
  диапазонах `dt`; источники с похожими именами), или принимает только явную инструкцию
  «слей X и Y».
- Как split задаёт предикат разбиения транзакций.
- Нужна ли операция логироваться (кто/когда слил) отдельно от журнала данных.

## Решение (для rename/merge `lbs`)

Принят вариант **A** — явное переписывание журнала, без слоя алиасов и без спец-событий.
`ds mv --src SRC --lb LB [--to-src SRC2] --to-lb LB2` (`StoragePort.lb_merge`) переносит
`lb`/`src` на каждой затронутой транзакции (активной и архивной) и сразу удаляет
ставшую сиротой запись показателя из `lbs` — без отдельного шага логирования и без
механического поиска кандидатов (только явная инструкция, как и предполагалось в
«Следующем шаге» ниже). Подробности — [`../reference/cli.md#ds-mv`](../reference/cli.md#ds-mv),
[`../reference/storage-port.md`](../reference/storage-port.md).

Это решение закрывает только подмножество «одна метка, rename/merge». Split, слияние
источников целиком и дедупликация `ids`/`vals` не затрагивались и используют тот же
вариант A по аналогии, но не реализованы — остаются в
[`../roadmap/entity-curation.md`](../roadmap/entity-curation.md) вместе с открытыми
подвопросами выше (детект кандидатов, формат предиката для split, отдельное
аудит-логирование).

## Следующий шаг (для оставшегося)

Split и слияние источников/`ids`/`vals` ещё не спроектированы — делать отдельной веткой,
не смешивая с другими пунктами роадмапа (самый широкий blast radius: схема, порт, оба
адаптера, весь периметр тестов).
