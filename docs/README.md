# Документация `ds`

`ds` — встраиваемый движок хранения историзированных данных из разнородных источников и
набор инструментов инженера данных для работы с ним. Он задаёт **формат хранения** (неизменяемый
журнал изменений с атрибуцией по источникам и восстановлением состояния на любой момент времени)
и покрывает операции нижнего уровня. Семантическая обработка, разрешение коллизий между
источниками и пользовательские интерфейсы — задача вышестоящего слоя и в этот репозиторий
не входят (см. [`explanation/scope-and-non-goals.md`](explanation/scope-and-non-goals.md)).

> Документация соответствует коду на версии **0.5.0a1**. Раздел «реализовано ↔ не реализовано»
> проходит по границе `reference/` (как есть) ↔ `roadmap/` (запланировано).

## Как устроена документация

Четыре жанра, не смешиваются:

| Раздел | Отвечает на вопрос | Для кого |
|---|---|---|
| [`explanation/`](explanation/) | *зачем* репозиторий и *почему* такие технические решения | тот, кто хочет понять систему |
| [`reference/`](reference/) | *как оно устроено сейчас*, строго по коду | тот, кто пишет код против контракта |
| [`guides/`](guides/) | *как сделать* конкретную задачу; обучение | инженер данных, который пользуется `ds` |
| [`decisions/`](decisions/) | *почему приняли именно это решение* (ADR) | тот, кто меняет архитектуру |

Плюс:
- [`roadmap/`](roadmap/) — что ещё сядет в ядро, но пока не реализовано;
- [`attic/`](attic/) — первоначальный замысел ноября 2025, **не соответствует коду**, сохранён для истории.

## Принципы оформления

1. **Один аспект на файл**, ~1 экран. Файл разросся — дели.
2. **`reference/` не выдумывает.** Примеры команд — реальный прогон; DDL и вывод `--help`
   копируются из кода/из запуска, не пишутся по памяти. Проверяется примерами в `../examples/`.
3. **Реализованное и запланированное не в одном файле.** Если фича есть в `reference/` — она
   работает в текущем теге. Если в `roadmap/` — её нет.
4. Язык — русский. Идентификаторы, имена таблиц/полей — как в коде.
