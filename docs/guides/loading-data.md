# Загрузка данных: пошаговая инструкция

> **Жанр:** how-to. Быстрый старт с нуля — [`getting-started.md`](getting-started.md).
> Справочники: [`../reference/cli.md`](../reference/cli.md),
> [`../reference/data-format.md`](../reference/data-format.md),
> [`../reference/config-format.md`](../reference/config-format.md).
> Как потом посмотреть состояние — [`reading-state-via-sql.md`](reading-state-via-sql.md)
> (команды `ds get` пока нет).

Этот документ описывает все ручные действия, необходимые для загрузки данных через `ds load`,
формат входных файлов и то, что происходит внутри при загрузке. Все примеры в этом файле —
не абстрактные: они получены реальным прогоном команд из этого репозитория (проверено на
`SQLiteAdapter`), так что вывод SQL-запросов ниже — настоящий, не придуманный.

---

## 0. Установка

Зависимостей, кроме стандартной библиотеки Python (3.9+), нет.

```bash
pip install -e .
```

После этого доступна команда `ds` (см. `pyproject.toml` → `[project.scripts]`). Либо можно
не устанавливать пакет, а запускать модуль напрямую из корня репозитория:

```bash
PYTHONPATH=. python3 -m src.cli.commands ...
```

Ниже везде используется просто `ds ...` — если пакет не установлен, замени на форму выше.

## 1. Ручные действия перед загрузкой

### 1.1 Создать папку конфигурации источника

Источник данных (например, "CRM", "ERP", "Сайт") описывается одним обязательным файлом
`source.json` в отдельной папке. Папку и файл создаёшь сам — никакого генератора для этого нет.

```
sources/
└── CRM/
    └── source.json
```

`source.json`:

```json
{
  "name": "CRM",
  "key_label": "customer_id"
}
```

| Поле | Обязательно | Что делает на практике |
|---|---|---|
| `name` | да | Имя источника — под этим именем он появится в БД. |
| `key_label` | да | Имя колонки в данных, которая содержит уникальный ID объекта. |
| `p` | нет | **Игнорируется загрузчиком.** Парсится, но никуда не передаётся при создании источника в БД — реальный вес всегда будет 0.5 по умолчанию, что бы тут ни было написано. Не трать время на подбор значения. |
| `description` | нет | Тоже парсится, но никуда не используется загрузчиком. |

Папку `labels/` внутри `sources/CRM/` создавать не нужно — она полностью необязательна и
никак не влияет на загрузку (даже если создать `labels/email/config.json`, `json_loader` в
него не заглядывает).

### 1.2 Подготовить файл с данными

Формат — **колоночный JSON**: каждый ключ верхнего уровня — имя колонки, значение — список
значений этой колонки. Все списки должны быть одной длины.

```json
{
  "customer_id": ["101", "102", "103"],
  "email":       ["alice@example.com", "bob@example.com", "carol@example.com"],
  "phone":       ["+7-900-000-0001", "+7-900-000-0002", null]
}
```

Правила:

- Колонка `key_label` (в этом примере — `customer_id`) обязана присутствовать, не может
  содержать `null`, и все значения в ней должны быть уникальны в пределах файла.
- Остальные колонки — любые, `null` означает "значение отсутствует / удалено".
- Не все колонки обязаны быть в каждом файле — можно грузить только часть показателей.
- Числа (`int`/`float`) в данных допустимы — автоматически приводятся к строке.

### 1.3 Запустить загрузку

```bash
ds --db data.db load sources/CRM batch_2024-01.json --dt 1704067200
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `--db` | нет (по умолчанию `data.db`) | путь к файлу SQLite; создаётся автоматически, если его нет |
| `source_dir` | да | папка с `source.json` (в примере — `sources/CRM`) |
| `data_file` | да | путь к JSON-файлу с данными |
| `--dt` | нет (по умолчанию — текущее время) | unix-timestamp: **когда данные актуальны** (бизнесовое время, не время запуска команды) |

Флага для выбора типа операции (`--act`) нет — он определяется автоматически (см. ниже).

## 2. Что происходит внутри при загрузке (по шагам)

На примере первого батча (`batch_2024-01.json` выше, `--dt 1704067200` = `2024-01-01 00:00:00 UTC`):

1. **Валидация** (`src/service/validate.py`): проверяется, что все колонки одной длины,
   `customer_id` есть, без `null` и без дублей. Если что-то не так — загрузка не начинается
   вообще, ничего не пишется в БД.
2. **Открывается транзакция БД** (`storage.begin()`) — весь батч либо загрузится целиком, либо
   не загрузится вообще (при ошибке — `rollback()`).
3. **Источник создаётся или находится**: `"CRM"` → запись в таблице `srcs` (создаётся при первом
   обращении, при повторных — находится существующая, дублей не будет). При создании `key_label`
   у источника ещё не задан (`NULL`) — метки не могут существовать раньше самого источника,
   потому что теперь они к нему привязаны (см. следующий шаг).
4. **Интернирование key_label**: строка `"customer_id"` превращается в целочисленный `lb_id`
   (таблица `lbs`), с привязкой к `src_id` источника из шага 3. Если такой метки для этого
   источника ещё не было — создаётся с `p=0.5` по умолчанию. Если у источника `key_label` ещё
   не был задан — он дозаписывается этим `lb_id` (`UPDATE srcs SET key_label = ...`).
5. **Интернирование остальных колонок** (`email`, `phone`) — тоже превращаются в `lb_id` в
   таблице `lbs`, каждая с привязкой к тому же `src_id`. Метки специфичны для источника: одна и
   та же колонка `email` в другом источнике получит свой, отдельный `lb_id`, даже если имя
   совпадает.
6. **Интернирование id**: каждое значение `customer_id` (`"101"`, `"102"`, `"103"`) превращается
   в `id_id` в таблице `ids`.
7. **Один запрос** к БД вытаскивает последнее известное состояние по всем парам `(метка, id)` из
   этого батча сразу — это нужно на следующем шаге для авто-определения типа операции.
8. **Построчно и по колонкам** (кроме `key_label`) для каждой ячейки:
   - если значение `null` → операция `DELETE`, значение в транзакции — пусто;
   - если для этой пары (источник, метка, id) раньше не было записи, либо последняя запись
     была удалением → операция `PATCH`;
   - если раньше уже было значение → операция `POST`.
   Непустое значение интернируется в таблицу `vals`, и вставляется строка в `transactions`.
9. **Commit** — все вставки этого батча фиксируются разом.

Первый батч (3 строки × 2 не-ключевые колонки = 6 ячеек, но `phone` для `103` — `null`, так что
это тоже засчитывается): команда вывела `loaded 6 transaction(s)` — 5 операций `PATCH` + 1 `DELETE`
(потому что для всех троих клиентов это первое появление).

## 3. Символический пример целиком

### Файлы

`sources/CRM/source.json`:
```json
{"name": "CRM", "key_label": "customer_id"}
```

`batch_2024-01.json` (загружен с `--dt 1704067200`, т.е. `2024-01-01 00:00:00 UTC`):
```json
{
  "customer_id": ["101", "102", "103"],
  "email":       ["alice@example.com", "bob@example.com", "carol@example.com"],
  "phone":       ["+7-900-000-0001", "+7-900-000-0002", null]
}
```

`batch_2024-02.json` (загружен позже, с `--dt 1706745600`, т.е. `2024-02-01 00:00:00 UTC`):
```json
{
  "customer_id": ["102", "104"],
  "email":       ["bob.new@example.com", "dave@example.com"]
}
```

### Команды

```bash
ds --db data.db load sources/CRM batch_2024-01.json --dt 1704067200
# loaded 6 transaction(s)

ds --db data.db load sources/CRM batch_2024-02.json --dt 1706745600
# loaded 2 transaction(s)
```

Во втором батче:
- `customer_id=102` уже имел значение `email` из первого батча → **POST** (перезапись).
- `customer_id=104` встречается впервые → **PATCH** (первое появление).

### Реальное содержимое таблиц после обеих загрузок

```
=== srcs ===
src_id  name  description  p    key_label
1       CRM   None         0.5  1

=== lbs ===
lb_id  name         description  p    src_id
1      customer_id  None         0.5  1
2      email        None         0.5  1
3      phone        None         0.5  1

=== ids ===
id_id  value
1      101
2      102
3      103
4      104

=== vals ===
val_id  value
1       alice@example.com
2       +7-900-000-0001
3       bob@example.com
4       +7-900-000-0002
5       carol@example.com
6       bob.new@example.com
7       dave@example.com

=== acts ===
act_id  name
1       PATCH
2       DELETE
3       POST

=== transactions (сырые данные, числовые id) ===
cnt  act  dt            src  lb  id  val   p    created_at
1    1    1704067200.0  1    2   1   1     1.0  1787710255.9749916
2    1    1704067200.0  1    3   1   2     1.0  1787710255.9753358
3    1    1704067200.0  1    2   2   3     1.0  1787710255.9755533
4    1    1704067200.0  1    3   2   4     1.0  1787710255.9758008
5    1    1704067200.0  1    2   3   5     1.0  1787710255.9759774
6    2    1704067200.0  1    3   3   None  1.0  1787710255.9761736
7    3    1706745600.0  1    2   2   6     1.0  1787710256.0905724
8    1    1706745600.0  1    2   4   7     1.0  1787710256.0907075
```

Обрати внимание: `val=None` в строке `cnt=6` — это и есть `DELETE` (телефон клиента 103
пришёл как `null`).

`created_at` — не бизнес-время (`dt`), а момент физической вставки записи (генерируется один раз
на сервере при вставке). В отличие от `dt` и `cnt`, значения выше **не воспроизведутся** при
повторном прогоне — это реальное время выполнения команды на момент подготовки этого документа,
приведено только для иллюстрации формата.

## 4. Примеры запросов к БД (sqlite3)

БД — обычный файл SQLite, открывается стандартным клиентом:

```bash
sqlite3 data.db
```

Ниже — рабочие запросы поверх примера из раздела 3, с реальным выводом.

### 4.1 Человеко-читаемый лог всех транзакций

Сырые `transactions` содержат только числовые `id` (ссылки на пулы). Чтобы увидеть имена,
нужен `JOIN` со всеми справочными таблицами:

```sql
SELECT
  t.cnt,
  a.name AS act,
  datetime(t.dt, 'unixepoch') AS dt,
  s.name AS source,
  l.name AS label,
  i.value AS id,
  v.value AS value
FROM transactions t
JOIN acts a ON a.act_id = t.act
JOIN srcs s ON s.src_id = t.src
JOIN lbs l  ON l.lb_id  = t.lb
JOIN ids i  ON i.id_id  = t.id
LEFT JOIN vals v ON v.val_id = t.val
ORDER BY t.cnt;
```

Вывод:

```
cnt  act     dt                   source  label  id   value
1    PATCH   2024-01-01 00:00:00  CRM     email  101  alice@example.com
2    PATCH   2024-01-01 00:00:00  CRM     phone  101  +7-900-000-0001
3    PATCH   2024-01-01 00:00:00  CRM     email  102  bob@example.com
4    PATCH   2024-01-01 00:00:00  CRM     phone  102  +7-900-000-0002
5    PATCH   2024-01-01 00:00:00  CRM     email  103  carol@example.com
6    DELETE  2024-01-01 00:00:00  CRM     phone  103
7    POST    2024-02-01 00:00:00  CRM     email  102  bob.new@example.com
8    PATCH   2024-02-01 00:00:00  CRM     email  104  dave@example.com
```

### 4.2 Текущее значение конкретного показателя ("последняя запись побеждает")

Готовой команды для чтения состояния сейчас нет (была `ds get` в `0.4.0a1`, убрана вместе с
остальным Processing Engine/Core API — будет переделана заново поверх текущей схемы). Пока что
единственный способ — SQL руками: взять последнюю по `cnt` транзакцию для нужной пары
`(источник, метка, id)`:

```sql
SELECT v.value
FROM transactions t
LEFT JOIN vals v ON v.val_id = t.val
WHERE t.src = (SELECT src_id FROM srcs WHERE name='CRM')
  AND t.lb  = (SELECT lb_id  FROM lbs  WHERE name='email')
  AND t.id  = (SELECT id_id  FROM ids  WHERE value='102')
ORDER BY t.cnt DESC
LIMIT 1;
```

Вывод:

```
value
bob.new@example.com
```

(то есть видно, что второй батч перекрыл значение из первого — так и задумано).

### 4.3 Количество транзакций по источнику

```sql
SELECT s.name, COUNT(*) AS txn_count
FROM transactions t JOIN srcs s ON s.src_id = t.src
GROUP BY s.name;
```

Вывод:

```
name  txn_count
CRM   8
```

### 4.4 Вся история конкретного объекта (видно DELETE)

```sql
SELECT t.cnt, a.name AS act, l.name AS label, v.value AS value
FROM transactions t
JOIN acts a ON a.act_id = t.act
JOIN lbs l  ON l.lb_id  = t.lb
LEFT JOIN vals v ON v.val_id = t.val
WHERE t.id = (SELECT id_id FROM ids WHERE value='103')
ORDER BY t.cnt;
```

Вывод:

```
cnt  act     label  value
5    PATCH   email  carol@example.com
6    DELETE  phone
```

## 5. На что обратить внимание при работе с реальными данными

- **Чтение состояния через CLI сейчас нет** — команда `ds get`, которая была в `0.4.0a1`, убрана
  вместе с остальным Processing Engine/Core API при откате к ядру (метки стали специфичны для
  источника, транзакции получили `created_at` — старую логику `fold_state`/`build_export`
  переписывать под новую схему решили отдельно, позже). До тех пор единственный способ узнать
  текущее или прошлое значение показателя — ручной SQL, как в разделе 4.
- **Метки (`lbs`) теперь специфичны для источника** (`UNIQUE(src_id, name)`, не просто `name`) —
  одноимённая колонка в разных `source.json` создаёт две разные записи в `lbs` с разными `lb_id`.
  Если нужно свести одноимённые показатели из разных источников в один — такого сопоставления
  в фреймворке пока нет.
- **`p` из `source.json` не работает** — если тебе нужны веса доверия источника, единственный
  способ сейчас — руками сделать `UPDATE srcs SET p = ... WHERE name = '...'` в БД напрямую (в
  коде это `StoragePort.src_update()`, но в CLI не выведено).
- **Каждый повторный запуск того же файла — это новые транзакции**, не перезапись. Append-only
  лог: если случайно загрузить один и тот же батч дважды, в БД появится по два комплекта
  транзакций (и `POST` вместо `PATCH` во второй раз, так как история уже будет).
- **`--dt` — это не время запуска команды**, а "с какого момента данные считаются актуальными".
  Если грузишь исторические выгрузки — используй реальную дату среза, а не текущее время.
- **Архивирование и удаление уже реализованы на уровне хранилища** (`txn_archive`, `txn_delete`),
  но не выведены в CLI — см. отдельное обсуждение модульности, если понадобится их включить.
