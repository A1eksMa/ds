## Архитектурные принципы

### 1. Event Sourcing / Журнал транзакций

Фреймворк использует подход **Event Sourcing**: вместо обновления данных "на месте", каждое изменение записывается как отдельная транзакция в журнал. Актуальное состояние восстанавливается путем "проигрывания" транзакций до нужного момента времени.

**Преимущества:**
- Полная история изменений (audit trail)
- Возможность восстановления состояния на любой момент времени ("машина времени")
- Отсутствие потери данных при обновлении

### 2. Dictionary Encoding для оптимизации хранения

Все текстовые данные (source, label, id, value) хранятся в отдельных справочных таблицах (**string pools**). В основной таблице транзакций хранятся только целочисленные ссылки.

**Преимущества:**
- Значительная экономия места (вместо повторяющихся строк — числа)
- Быстрее сравнения (INTEGER vs TEXT)
- Компактные индексы
- Экономия RAM при загрузке данных

### 3. Снэпшоты (Checkpoints) для оптимизации

Для избежания полного пересчета состояния каждый раз создаются **снэпшоты** — сохраненные состояния на определенный момент времени. Новое состояние получается наложением инкрементальных изменений на последний снэпшот.

## Терминология

| Термин | Описание | Пример |
|--------|----------|--------|
| **Source** | Источник информации | "CRM", "ERP", "Website" |
| **Label** | Показатель, индикатор, заголовок столбца | "Email", "Phone", "Price", "Stock" |
| **ID** | Уникальный идентификатор объекта (значение ключевого label для данного source) | customer_id=12345 |
| **Value** | Конкретное значение показателя | "moscow@example.com", "+7-123-456" |
| **Key Label** | Ключевой показатель для источника, содержащий уникальные ID | "customer_id", "product_id" |
| **p (вес доверия)** | Числовое значение от 0.0 до 1.0, характеризующее достоверность данных | 0.9 для ERP, 0.5 для Website |

**Четыре измерения данных:**
```
Source → Label → ID → Value
```

> **Уточнение (принято по итогам обсуждения):** `Label` не является независимым от `Source`
> измерением — метка существует только в контексте конкретного источника. Одинаковое имя метки
> в разных источниках может означать разные сущности (и наоборот), поэтому `lbs` не глобальный пул
> по имени, а пул, уникальный в паре `(src_id, name)` — см. схему таблицы `lbs` ниже. Кросс-источниковое
> сопоставление одноимённых показателей (нужное для Level 2) требует отдельного явного слоя
> соответствия меток между источниками, которого на момент этого документа нет.

**Пример входных данных (JSON):**
```json
{
  "customer_id": [1, 2, 3],
  "email": ["a@example.com", "b@example.com", "c@example.com"],
  "phone": ["+123", "+456", "+789"]
}
```
где `customer_id` — ключевой label для данного source.

## Гибридная архитектура

Система использует комбинацию БД и файловой системы:

### SQLite БД
- Хранит фактические данные (транзакции)
- Хранит справочники (string pools)
- Хранит метаданные (имена, описания, веса доверия)
- Хранит текущее состояние (один актуальный снэпшот)

### Файловая система

**Конфигурационные файлы** (JSON/YAML/TOML):
```
/
├── database.db
├── config.yaml                    # Глобальное описание БД
└── sources/
    ├── CRM/
    │   ├── source.yaml            # Описание источника (опционально)
    │   └── labels/
    │       ├── Email/
    │       │   └── config.yaml    # Специфичные параметры показателя
    │       └── Phone/
    │           └── config.yaml
    └── ERP/
        └── ...
```

**Что хранится в конфигах:**
- `data_type` — тип данных ('email', 'phone', 'number', 'date', etc.)
- `validators` — правила валидации
- `handlers` — обработчики для преобразования данных
- Другие специфичные параметры для отдельных показателей

**Архив снэпшотов:**
```
snapshots/
├── state_2025-10-01_v1.json
├── state_2025-10-08_v1.json
└── state_2025-10-15_v1.json
```

Каждый файл снэпшота содержит:
- Данные (актуальное состояние)
- Метаданные (timestamp, базовый снэпшот, количество примененных транзакций, хеши конфигов)

## Структура базы данных

### Справочные таблицы (String Pools)

#### cnts — Счетчики транзакций
```sql
CREATE TABLE cnts (
    cnt_id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at REAL NOT NULL DEFAULT (julianday('now'))  -- Техническая метка времени
);
```

**Назначение:** Центральный генератор уникальных идентификаторов для транзакций.

**Обоснование решения:** Выделение счетчика в отдельную таблицу обеспечивает 100% уникальность cnt при перемещении записей между основной таблицей и архивом. Следует паттерну string pools и позволяет атомарно перемещать данные без конфликтов ключей.

---

#### acts — Операции (коды транзакций)
```sql
CREATE TABLE acts (
    act_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL  -- 'POST', 'GET', 'PATCH', 'DELETE'
);
```

**Назначение:** Справочник типов операций в стиле REST API.

---

#### srcs — Источники данных
```sql
CREATE TABLE srcs (
    src_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL,          -- Уникальное имя источника
    description TEXT,                    -- Полное описание (опционально)
    p REAL DEFAULT 0.5,                  -- Доверительная вероятность источника
    key_label INTEGER,                   -- Ссылка на ключевой label; NULL до бутстрапа
    FOREIGN KEY (key_label) REFERENCES lbs(lb_id)
);
```

**Назначение:** Справочник источников информации с метаданными.

**Поля:**
- `name` — краткое уникальное имя (например, "CRM", "ERP")
- `description` — развернутое описание источника
- `p` — вес доверия для всего источника (по умолчанию 0.5 — середина шкалы)
- `key_label` — ссылка на показатель, который содержит уникальные ID объектов для этого источника.
  `NULL` до момента бутстрапа (см. ниже) — ключевая метка не может быть создана раньше самого
  источника, поскольку `lbs.src_id` обязателен.

**Бутстрап `Src` ↔ `Lb` (разрыв циклической зависимости):** `srcs.key_label` ссылается на `lbs`,
а `lbs.src_id` ссылается на `srcs` — создать обе записи одним шагом невозможно. Порядок:
1. Создать `Src` с `key_label = NULL`.
2. Создать `Lb` ключевого показателя с уже существующим `src_id`.
3. `UPDATE srcs SET key_label = <lb_id>`.

---

#### lbs — Показатели (Labels)
```sql
CREATE TABLE lbs (
    lb_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,                  -- Имя показателя, уникальное в рамках источника
    description TEXT,                    -- Полное описание (опционально)
    p REAL DEFAULT 0.5,                  -- Доверительная вероятность показателя
    src_id INTEGER NOT NULL,             -- Метки специфичны для источника (см. "Терминология")
    UNIQUE (src_id, name),
    FOREIGN KEY (src_id) REFERENCES srcs(src_id) ON DELETE RESTRICT
);
```

**Назначение:** Справочник показателей (индикаторов), специфичных для источника.

**Поля:**
- `name` — краткое имя (например, "Email", "Phone", "Price"), уникальное только в паре с `src_id`
- `src_id` — источник, к которому относится метка; одноимённые метки разных источников — разные
  записи с разными `lb_id`
- `description` — развернутое описание показателя
- `p` — вес доверия для показателя (переопределяет вес источника при расчете)

---

#### ids — Идентификаторы объектов
```sql
CREATE TABLE ids (
    id_id INTEGER PRIMARY KEY AUTOINCREMENT,
    value TEXT UNIQUE NOT NULL
);
```

**Назначение:** Пул уникальных идентификаторов объектов (customer_id, product_id и т.д.).

**Примечание:** Хранит только уникальные значения ID в текстовом виде.

---

#### vals — Значения
```sql
CREATE TABLE vals (
    val_id INTEGER PRIMARY KEY AUTOINCREMENT,
    value TEXT UNIQUE NOT NULL
);
```

**Назначение:** Пул уникальных значений показателей.

**Примечание:** Все значения хранятся в текстовом формате. Типизация и обработка происходит на уровне Processing Engine с использованием конфигов.

---

### Основная таблица

#### transactions — Журнал транзакций
```sql
CREATE TABLE transactions (
    cnt INTEGER PRIMARY KEY,                 -- Ссылка на cnts.cnt_id
    act INTEGER NOT NULL,                    -- Тип операции
    dt REAL NOT NULL,                        -- Timestamp (бизнесовый)
    src INTEGER NOT NULL,                    -- Источник
    lb INTEGER NOT NULL,                     -- Показатель
    id INTEGER NOT NULL,                     -- ID объекта
    val INTEGER,                             -- Значение (NULL для DELETE)
    p REAL DEFAULT 1.0,                      -- Вес доверия записи (p_record)
    created_at REAL NOT NULL,                -- Когда запись физически попала в БД (не бизнес-время)

    FOREIGN KEY (cnt) REFERENCES cnts(cnt_id) ON DELETE RESTRICT,
    FOREIGN KEY (act) REFERENCES acts(act_id) ON DELETE RESTRICT,
    FOREIGN KEY (src) REFERENCES srcs(src_id) ON DELETE RESTRICT,
    FOREIGN KEY (lb) REFERENCES lbs(lb_id) ON DELETE RESTRICT,
    FOREIGN KEY (id) REFERENCES ids(id_id) ON DELETE RESTRICT,
    FOREIGN KEY (val) REFERENCES vals(val_id) ON DELETE RESTRICT
);
```

---

#### transactions_archive — Архив транзакций
```sql
CREATE TABLE transactions_archive (
    cnt INTEGER PRIMARY KEY,                 -- Ссылка на cnts.cnt_id
    act INTEGER NOT NULL,                    -- Тип операции
    dt REAL NOT NULL,                        -- Timestamp (бизнесовый)
    src INTEGER NOT NULL,                    -- Источник
    lb INTEGER NOT NULL,                     -- Показатель
    id INTEGER NOT NULL,                     -- ID объекта
    val INTEGER,                             -- Значение (NULL для DELETE)
    p REAL DEFAULT 1.0,                      -- Вес доверия записи (p_record)
    created_at REAL NOT NULL,                -- Когда запись физически попала в БД (не бизнес-время)

    FOREIGN KEY (cnt) REFERENCES cnts(cnt_id) ON DELETE RESTRICT,
    FOREIGN KEY (act) REFERENCES acts(act_id) ON DELETE RESTRICT,
    FOREIGN KEY (src) REFERENCES srcs(src_id) ON DELETE RESTRICT,
    FOREIGN KEY (lb) REFERENCES lbs(lb_id) ON DELETE RESTRICT,
    FOREIGN KEY (id) REFERENCES ids(id_id) ON DELETE RESTRICT,
    FOREIGN KEY (val) REFERENCES vals(val_id) ON DELETE RESTRICT
);
```

**Назначение:** Основное хранилище операций с данными + архивная таблица для партиционирования.

**Структура партиционирования:**
- `transactions` — активные данные для текущих операций
- `transactions_archive` — архивированные данные (идентичная структура)
- Записи могут атомарно перемещаться между таблицами без изменения `cnt`

**Поля:**
- `cnt` — ссылка на уникальный идентификатор из таблицы `cnts`
- `act` — тип операции (POST/GET/PATCH/DELETE)
- `dt` — бизнесовый timestamp, когда данные стали актуальны (может быть задан извне)
- `src` — источник данных
- `lb` — показатель
- `id` — идентификатор объекта
- `val` — значение (NULL для операции DELETE)
- `p` — вес доверия конкретной записи (p_record)
- `created_at` — технический timestamp физической вставки записи (генерируется storage-слоем
  один раз при вставке); отдельно от `dt` (бизнес-время) и `cnt` (порядок вставки). Нужен для
  объяснения расхождений между отчётами при задержанной доставке данных от источника.

**Ключевое различие `cnt` и `dt`:**
- `cnt` — технический, ссылка на `cnts.cnt_id`, обеспечивает уникальность во всей системе
- `dt` — бизнесовый, может быть любым, определяет "когда данные актуальны"

**Внешние ключи с политикой RESTRICT:**
Все foreign keys имеют политику `ON DELETE RESTRICT` для защиты от случайного удаления связанных данных.

### Таблица состояния (State)

#### state — Текущий снэпшот
```sql
CREATE TABLE state (
    src INTEGER NOT NULL,                    -- Источник
    lb INTEGER NOT NULL,                     -- Показатель
    id INTEGER NOT NULL,                     -- ID объекта
    val INTEGER,                             -- Значение (NULL для удаленных записей)

    PRIMARY KEY (src, lb, id),
    FOREIGN KEY (src) REFERENCES srcs(src_id) ON DELETE RESTRICT,
    FOREIGN KEY (lb) REFERENCES lbs(lb_id) ON DELETE RESTRICT,
    FOREIGN KEY (id) REFERENCES ids(id_id) ON DELETE RESTRICT,
    FOREIGN KEY (val) REFERENCES vals(val_id) ON DELETE RESTRICT
);
```

**Назначение:** Хранит ONE актуальный снэпшот состояния на определенный момент времени.

**Обоснование структуры:** Таблица содержит только ключевые поля данных (src, lb, id, val), исключая служебные поля из transactions (act, dt, p, cnt). Это упрощает структуру и ускоряет операции чтения. Метаданные снэпшота хранятся в отдельных файлах.

**Особенности:**
- Это производная таблица, рассчитываемая из transactions
- Хранится только ОДИН снэпшот (перезаписывается)
- Архив снэпшотов ведется на файловом уровне
- Может быть построена двумя путями:
  1. Расчетом из таблицы transactions (прямой/обратный метод)
  2. Загрузкой из ранее выгруженного файла

**Workflow работы со снэпшотами:**
1. Расчет snapshot на момент t1 → Выгрузка в файл
2. Накопление транзакций (t1..t2)
3. Инкрементальное обновление: на состояние t1 накладываются транзакции (t1, t2]
4. Выгрузка нового состояния t2 → передача дальше по конвейеру
5. Возможность отката: обратным методом вернуться к состоянию t1

## Концепция работы

### Расчет итогового веса доверия

Итоговый вес рассчитывается **динамически** в момент запроса с учетом **текущих** значений в БД:

```
p_total = p_source × p_label × p_record
```

где:
- `p_source` — из таблицы `srcs.p`
- `p_label` — из таблицы `lbs.p`
- `p_record` — из таблицы `transactions.p`

**Важно:**
- Веса в БД (`p_source`, `p_label`) могут быть изменены в любой момент
- При изменении весов **все исторические запросы** будут пересчитаны с новыми весами
- Веса **не версионируются** (не привязаны ко времени)
- Если для label не задан свой вес, используется дефолтное значение 0.5 (не наследуется от source)

### Алгоритм построения снэпшота с чекпоинтами

```
История: [t0] ----транзакции----> [t1] ----транзакции----> [t2] ----транзакции----> [сейчас]
                                  ↑                          ↑
                             snapshot_1                 snapshot_2

Чтобы получить состояние на t1.5:
1. Берем snapshot_1 (состояние на t1, last_cnt=1523)
2. Применяем транзакции WHERE cnt > 1523 AND dt <= t1.5
3. Получаем состояние на t1.5
```

### Разрешение коллизий

При построении среза данных, если для одного объекта (source + id) найдено несколько значений одного показателя:

1. Сравниваются `p_total` для каждого значения
2. Выбирается значение с наибольшим `p_total`
3. При равных весах — выбирается более свежее (по `dt`)

### Индексы для оптимизации

```sql
-- Основная таблица
CREATE INDEX idx_transactions_dt ON transactions(dt);
CREATE INDEX idx_transactions_src_lb_id ON transactions(src, lb, id);

-- Архивная таблица
CREATE INDEX idx_transactions_archive_dt ON transactions_archive(dt);
CREATE INDEX idx_transactions_archive_src_lb_id ON transactions_archive(src, lb, id);
```

**Обоснование:**
- `idx_*_dt` — для фильтрации по времени в запросах "машины времени"
- `idx_*_src_lb_id` — для группировки данных по объектам при построении состояний

### Объединенный доступ

```sql
-- VIEW для ретроспективного анализа с объединением основной и архивной таблиц
CREATE VIEW transactions_full AS
SELECT * FROM transactions
UNION ALL
SELECT * FROM transactions_archive
ORDER BY cnt;
```

**Обоснование:** Обеспечивает прозрачный доступ ко всем данным при необходимости глубокого ретроспективного анализа.

## Принятые архитектурные решения

### 1. ✅ Структура таблицы state
**Решение:** Упрощенная копия transactions только с ключевыми полями (src, lb, id, val).
**Обоснование:** Максимальная простота структуры при сохранении консистентности с остальной архитектурой.

### 2. ✅ Формат выгрузки снэпшотов
**Решение:** JSON с двумя основными форматами:
- Внутренний снэпшот: `{metadata, data}`
- Формат выгрузки: `{metadata, data, configs}`

**Обоснование:** JSON обеспечивает консистентность с общей архитектурой фреймворка и читаемость.

### 3. ✅ Семантика операций DELETE
**Решение:** DELETE с `val = NULL` показывает удаление значения из источника.
**Обоснование:** REST API используется только в рамках одного источника. DELETE исключает значение из расчетов до появления нового POST.

### 4. ✅ Партиционирование
**Решение:** Две таблицы (transactions + transactions_archive) + выделенная таблица счетчиков (cnts).
**Обоснование:** Простое решение ограничений SQLite с гарантией уникальности ключей + возможность восстановления + атомарность операций.

### 5. ✅ Индексы для оптимизации
**Решение:** Индексы на `dt` и составной `(src, lb, id)` для обеих таблиц.
**Обоснование:** Покрывают основные паттерны запросов фреймворка.

### 6. ✅ Политики внешних ключей
**Решение:** `ON DELETE RESTRICT` для всех foreign keys.
**Обоснование:** Максимальная защита от случайного удаления данных. Требует явного порядка операций при удалении.

### 7. ✅ Оптимизация string pools
**Решение:** Гибридный подход:
- Маленькие pools (srcs, lbs, ids, acts) — кеширование в памяти
- Большие pools (vals) — простые запросы без кеширования

**Обоснование:** Баланс между простотой реализации и производительностью с учетом ограничений RAM.

## Примечания

- Все веса доверия (`p`) по умолчанию установлены в **0.5** (середина шкалы 0.0-1.0)
- БД является **единственным источником правды** для весов доверия
- Конфиги используются только для специфичных параметров обработки данных
- Таймстампы хранятся как `REAL` (Unix timestamp в секундах с дробной частью)
- **DELETE-операции:** `val = NULL` означает удаление значения из источника на указанный момент времени
- **Партиционирование:** Записи атомарно перемещаются между основной и архивной таблицами
- **Уникальность cnt:** Обеспечивается выделенной таблицей `cnts` для всей системы
- **Защита данных:** Политика `RESTRICT` предотвращает случайное удаление связанных записей
