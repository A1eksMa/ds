# Архитектура компонентов фреймворка

> Дата: 2025-11-05 (обновлено с двухуровневой логикой)
> Статус: Финализировано с многоуровневой обработкой данных

---

## Обзор компонентов

Фреймворк состоит из 11 основных компонентов с двухуровневой архитектурой обработки данных:

**Уровень 1 (Single Source):** Логика работы с отдельными источниками данных
**Уровень 2 (Multi Source):** Интеграция данных из множественных источников с семантическим маппингом

---

## 1. CLI (Command Line Interface)

**Расположение:** `src/cli/`

**Назначение:** Точка входа для пользователя

**Ответственность:**
- Парсинг команд и аргументов с использованием `argparse`
- Валидация входных параметров на уровне CLI
- Маршрутизация команд к соответствующим методам Core API
- Обработка пользовательского ввода и вывода результатов

**Ключевые файлы:**
- `parser.py` — конфигурация argparse, определение команд и аргументов
- `commands.py` — обработчики конкретных команд

---

## 2. Core API

**Расположение:** `src/core/`

**Назначение:** Центральный координатор системы

**Ответственность:**
- Оркестрация вызовов всех других компонентов
- Реализация бизнес-логики высокого уровня
- Управление жизненным циклом операций (загрузка → обработка → выгрузка)
- Координация между компонентами для выполнения сложных операций

**Ключевые файлы:**
- `api.py` — основной API класс с публичными методами
- `orchestrator.py` — логика координации между компонентами

---

## 3. Storage Engine

**Расположение:** `src/storage/`

**Назначение:** Слой абстракции для работы с базой данных

**Ответственность:**
- Создание и инициализация базы данных SQLite
- Выполнение всех SQL-запросов (CRUD операции)
- Управление транзакциями БД, включая атомарные операции архивирования
- Партиционирование данных между основной и архивной таблицами
- Обеспечение целостности данных

**Ключевые файлы:**
- `engine.py` — основной класс для работы с БД
- `schema.py` — создание схемы БД, миграции
- `transactions.py` — управление транзакциями и атомарными операциями

---

## 4. String Pool Manager

**Расположение:** `src/pools/`

**Назначение:** Оптимизированная работа с пулами строковых значений

**Ответственность:**
- Реализация гибридной стратегии:
  - Кеширование в памяти для маленьких pools (srcs, lbs, ids, acts)
  - Простые SQL-запросы для больших pools (vals)
- Управление уникальностью значений в пулах
- Batch-операции при необходимости
- Оптимизация производительности при работе со строковыми данными

**Ключевые файлы:**
- `manager.py` — координация работы всех пулов
- `small_pool.py` — кешируемые пулы для частых операций
- `large_pool.py` — простые пулы для больших объемов данных

---

## 5. Data Loader

**Расположение:** `src/loader/`

**Назначение:** Загрузка и валидация входных данных

**Ответственность:**
- Чтение JSON-файлов с входными данными
- Валидация структуры и содержимого данных
- Преобразование внешних форматов во внутренние структуры данных
- Интеграция с String Pool Manager для эффективной обработки строк
- Обработка ошибок при загрузке данных

**Ключевые файлы:**
- `json_loader.py` — загрузка и парсинг JSON данных
- `validator.py` — валидация структуры и бизнес-правил

---

## 6. Processing Engine (Двухуровневая архитектура)

**Расположение:** `src/processing/`

**Назначение:** "Мозг" системы — реализация двухуровневой бизнес-логики обработки данных

**Архитектура:** Компонент разделен на два уровня абстракции для решения различных типов коллизий и преобразований данных.

### Уровень 1: Single Source Processing
**Ответственность:**
- Обработка данных в рамках одного источника
- Разрешение **временных коллизий** (более поздние данные приоритетнее)
- Нормализация и валидация данных по конфигам источника
- Типизация данных (email, phone, number, date, etc.)
- Применение REST API операций (POST, GET, PATCH, DELETE)

### Уровень 2: Multi Source Integration
**Ответственность:**
- Интеграция данных из множественных источников
- Разрешение **коллизий по весам доверия** между источниками
- Применение семантического маппинга (source labels → global entities)
- Объединение данных в единую консистентную модель
- Построение финальных срезов с учетом всех источников

**Ключевые подкомпоненты:**
- `engine.py` — главный координатор двух уровней
- `single_source/` — компоненты уровня 1
- `multi_source/` — компоненты уровня 2
- `semantic/` — семантический маппинг и разрешение сущностей

---

## 7. Entity Manager (НОВЫЙ)

**Расположение:** `src/entities/`

**Назначение:** Управление глобальными сущностями и семантическим маппингом

**Ответственность:**
- Управление глобальным реестром сущностей (Contract, Price, Customer, etc.)
- Маппинг между локальными именами источников и глобальными сущностями
- Разрешение семантических конфликтов (Contract = Договор = Agreement)
- Валидация консистентности маппингов
- Поддержка вариантов сущностей (PriceWithTax vs PriceWithoutTax)

**Примеры решаемых задач:**
- CRM.Contract_Number → Entity.Contract
- ERP.Agreement_ID → Entity.Contract
- CRM.Final_Price → Entity.Price.PriceWithTax
- ERP.Net_Price → Entity.Price.PriceWithoutTax

**Ключевые файлы:**
- `manager.py` — основной менеджер глобальных сущностей
- `mapper.py` — логика маппинга source → entity
- `validator.py` — валидация семантической консистентности

---

## 8. Config Manager (Расширенный)

**Расположение:** `src/config/`

**Назначение:** Работа с многоуровневой конфигурационной системой

**Ответственность:**
- Чтение конфигураций источников из `data/sources/[source]/`
- **НОВОЕ:** Управление глобальными сущностями из `data/sources/entities/`
- **НОВОЕ:** Обработка семантических маппингов из `data/sources/mappings/`
- Валидация согласованности конфигураций между уровнями
- Предоставление метаданных для всех компонентов системы
- Поддержка изменения путей к конфигурационным файлам

**Типы конфигураций:**
1. **Source-level:** Конфиги отдельных источников (CRM/, ERP/)
2. **Entity-level:** Глобальные сущности (entities/)
3. **Mapping-level:** Семантические маппинги (mappings/)

**Ключевые файлы:**
- `manager.py` — координация всех типов конфигураций
- `yaml_parser.py` — парсинг и валидация YAML файлов
- `entity_config.py` — **НОВОЕ:** работа с конфигами сущностей
- `mapping_config.py` — **НОВОЕ:** работа с маппингами

---

## 9. Snapshot Manager

**Расположение:** `src/snapshots/`

**Назначение:** Управление снэпшотами состояний системы с поддержкой двухуровневой архитектуры

**Ответственность:**
- Создание снэпшотов из обработанных данных (уровень 1 + уровень 2)
- Инкрементальные обновления существующих снэпшотов
- Выгрузка снэпшотов в файлы:
  - **Source-level snapshots:** состояния отдельных источников
  - **Integrated snapshots:** объединенные состояния с entity mapping
- Загрузка состояний из ранее сохраненных файлов
- Управление метаданными снэпшотов и их версионностью

**Ключевые файлы:**
- `manager.py` — управление жизненным циклом снэпшотов
- `builder.py` — алгоритмы построения снэпшотов из транзакций
- `exporter.py` — выгрузка снэпшотов в различные форматы
- `level_manager.py` — **НОВОЕ:** координация снэпшотов разных уровней

---

## 10. Archive Manager

**Расположение:** `src/archive/`

**Назначение:** Управление жизненным циклом данных и архивированием

**Ответственность:**
- Атомарное перемещение данных из основной таблицы в архив
- Восстановление данных из архива обратно в основную таблицу
- Физическое удаление данных ("жесткое" удаление)
- Очистка неиспользуемых записей в string pools
- Реализация политик хранения данных
- **НОВОЕ:** Архивирование с учетом семантических связей

**Ключевые файлы:**
- `manager.py` — управление операциями архивирования
- `lifecycle.py` — политики и алгоритмы жизненного цикла данных
- `entity_aware_archive.py` — **НОВОЕ:** архивирование с учетом entity mappings

---

## 11. Utils (Общие утилиты)

**Расположение:** `src/utils/`

**Назначение:** Общие вспомогательные компоненты

**Ответственность:**
- Централизованное логирование с поддержкой двухуровневой архитектуры
- Кастомные исключения для разных уровней обработки
- Вспомогательные функции для работы с данными
- **НОВОЕ:** Утилиты для семантического анализа
- **НОВОЕ:** Валидаторы для entity mappings

**Ключевые файлы:**
- `logging.py` — логирование с контекстом уровня обработки
- `exceptions.py` — исключения для single/multi source обработки
- `helpers.py` — общие вспомогательные функции
- `semantic_utils.py` — **НОВОЕ:** утилиты для семантического маппинга
- `validation_utils.py` — **НОВОЕ:** общие валидаторы

## Поток обработки данных

### 1. Уровень 1 (Single Source Processing)
```
Input JSON → Data Loader → Config Manager (source configs) →
Processing Engine (Level 1) →
├─ Time Resolver (временные коллизии)
├─ Normalizer (типизация и валидация)
└─ REST API Operations (POST/GET/PATCH/DELETE)
→ Storage Engine (transactions table)
```

### 2. Уровень 2 (Multi Source Integration)
```
Storage Engine → Processing Engine (Level 2) →
├─ Entity Manager (семантический маппинг)
├─ Semantic Mapping (source labels → global entities)
├─ Conflict Resolver (веса доверия между источниками)
└─ Entity Merger (объединение данных)
→ Storage Engine (state table) → Snapshot Manager
```

## Принципы взаимодействия

1. **Двухуровневая обработка:** Четкое разделение single-source и multi-source логики
2. **Семантическая прозрачность:** Entity Manager обеспечивает единообразное понимание данных
3. **Конфигурационная гибкость:** Трехуровневая система конфигов (source/entity/mapping)
4. **Слабая связанность:** Компоненты взаимодействуют через четко определенные интерфейсы
5. **Централизованное хранение:** Все данные проходят через Storage Engine
6. **Валидация на каждом уровне:** Каждый компонент проверяет консистентность своего уровня
