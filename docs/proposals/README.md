## Введение

**[Название Фреймворка]** — это внутрикорпоративный фреймворк с интерфейсом командной строки (CLI), предназначенный для построения конвейеров по обработке и анализу больших объемов данных.

### Назначение и решаемые проблемы

Основная цель фреймворка — автоматизировать и систематизировать работу с данными, поступающими из разнородных источников. Он был создан для решения следующих ключевых проблем:

*   **Большие объемы данных:** Ручная обработка и анализ данных становятся неэффективными и трудоемкими при значительном росте их объемов.
*   **Сложность алгоритмов:** Работа со сложными и неоднозначными правилами обработки данных требует системного подхода.
*   **Управление происхождением данных (Data Lineage):** Фреймворк обеспечивает полное отслеживание жизненного цикла данных:
    *   Фиксация источника и времени получения исходной информации.
    *   Логирование всех изменений.
    *   Прозрачное разрешение коллизий, возникающих при получении одних и тех же данных из разных источников.

### Ключевые особенности

Несмотря на то, что фреймворк разрабатывается как внутренняя утилита, его архитектура позволяет применять его в других организациях и предметных областях для решения задач по управлению неполными и противоречивыми данными.

*   **Входные данные:** Фреймворк оперирует **плоскими таблицами**, которые представляют собой срезы состояния различных систем (базы данных, отчеты, выгрузки) на определенный момент времени.
*   **Приоритезация источников:** Источники данных ранжируются по **приоритетности (весу доверия)** и **актуальности**. Это позволяет автоматически формировать наиболее достоверную и актуальную версию информации из противоречивых сведений.
*   **Гибкий анализ:** Каждый источник характеризуется набором показателей. Фреймворк позволяет гибко выбирать релевантные показатели для анализа.
*   **Ретроспективный анализ:** Все исторические данные сохраняются в базе данных, что позволяет в любой момент времени добавлять в анализ любые ранее полученные показатели.

## Функциональные требования

### 1. Управление данными на основе времени ("Машина времени")

Ключевой функцией фреймворка является возможность построения и анализа си��темы показателей на любой произвольный момент времени.

*   **Реконструкция состояния:** Система должна позволять пользователю получить полный срез данных и рассчитать все показатели так, как они выглядели бы на любую указанную дату и время в прошлом.
*   **Анализ временных рядов:** Пользователь должен иметь возможность отслеживать как общую динамику системы показателей, так и историю изменений отдельного показателя.
*   **Архивное хранение:** Все поступающие данные в неизменном виде архивируются в базе данных для обеспечения полной ретроспективы.
*   **Обработка несинхронизированных источников:** Фреймворк корректно обрабатывает данные от источников с разной периодичностью обновления.

#### Примеры работы "Машины времени"

> **Пример 1: Сборка актуального профиля из одного источника**
>
>Представим, что есть источник **"CRM-система"**, который хранит данные о клиенте. Обновления для разных полей приходят в разное время:
> *   `Email` клиента обновлен `2025-10-15`.
> *   `Телефон` клиента обновлен `2025-10-10`.
> *   `Статус` клиента изменен на "VIP" `2025-10-12`.
>
>При запросе актуальной информации фреймворк соберет "срез", взяв последнее известное значение для каждого показателя: `Email` от 15-го числа, `Телефон` от 10-го и `Статус` от 12-го.

> **Пример 2: Построение среза на прошлую дату**
>
>Используя те же данные, пользователь может сделать запрос "показать профиль клиента на `2025-10-11`".
>
>Фреймворк проигнорирует изменения от 12-го и 15-го числа и вернет срез, актуальный на тот момент: `Телефон` от 10-го числа и более старые значения `Email` и `Статуса`.

### 2. Управление данными на основе веса доверия (p)

Для разрешения коллизий, когда разные источники предоставляют противоречивую информацию, вводится система **весов доверия (p)**.

*   **Вес доверия (p):** Каждому источнику и/или показателю назначается числовое значение от 0.0 до 1.0, где `1.0` означает максимальное доверие, а `0.0` — минимальное.
*   **Гибкая настройка:** Вес доверия может быть наз��ачен как на весь **источник данных** целиком, так и на **отдельный показатель** внутри источника.
*   **Прозрачное разрешение коллизий:** При построении среза данных, если для одного и того же объекта найдена информация из нескольких источников, фреймворк автоматически выбирает значение из источника с наивысшим весом `p`. Вес показателя имеет более высокий приоритет, чем общий вес источника.

#### Примеры работы системы весов доверия

> **Пример 1: Вес на уровне источников**
>
>Есть два источника данных о товарах:
> *   **Источник А: "ERP-система"** (Вес доверия: `p=0.9`). Считается "источником правды".
> *   **Источник Б: "Публичный сайт"** (Вес доверия: `p=0.5`). Данные могут меняться для маркетинговых акций.
>
>По товару "X" есть следующие данные:
> *   Цена в ERP: `99.00` (данные от `2025-10-01`).
> *   Цена на Сайте: `95.00` (данные от `2025-10-14`).
>
>Несмотря на то, что данные с сайта новее, при запросе актуальной цены фреймворк выберет значение `99.00`, так как вес доверия ERP-системы (`p=0.9`) выше, чем у сайта (`p=0.5`).

> **Пример 2: Переопределение веса на уровне показателя**
>
>Допустим, мы знаем, что информация об остатках на складе (`Stock`) на сайте всегда точнее, так как обновляется в реальном времени. Мы можем задать особый вес для этого показателя.
>
> *   **Источник А: "ERP-система"** (Глобальный вес: `p=0.9`).
> *   **Источник Б: "Публичный сайт"** (Глобальный вес: `p=0.5`, но для показателя `Stock` вес: `p=0.95`).
>
>Данные по остаткам товара "X":
> *   Остаток в ERP: `150` шт. (данные от `2025-10-01`).
> *   Остаток на Сайте: `145` шт. (данные от `2025-10-15`).
>
>Теперь при запросе остатков фреймворк сравнит вес показателя `Stock` с сайта (`p=0.95`) с глобальным весом ERP (`p=0.9`) и выберет значение `145` шт. как более достоверное.

### 3. Управление жизненным циклом данных

Поскольку объем данных постоянно накапливается, фреймворк должен предоставлять инструменты для управления физическим хранилищем.

*   **Логическое разделение данных:** Система должна поддерживать разделение (партиционирование) данных на управляемые блоки, например, по временным периодам. Это является основой для эффективного архивирования и удаления.
*   **Архивирование ("мягкое" удаление):** Должна быть предусмотрена возможность перемещать устаревшие или редко используемые данные в отдельное архивное хранилище. Это позволяет освободить место в основной базе данных, сохраняя при этом возможность доступа к истории. **Пример:** архивировать все данные, полученные до `2024-01-01`.
*   **Физическое удаление ("жесткое" удаление):** Система должна предоставлять функционал для полного и безвозвратного удаления данных по заданным критериям. Это необходимо для соблюдения политик хранения данных и управления объемом хранилища. **Пример:** удалить все записи по показателю "Temporary_Metric" из источника "Legacy_System".

## Технические требования и ограничения

### 1. Технологический стек

*   **Язык программирования:** Python `3.9.20`. Использование данной версии является строгим требованием.
*   **База данных:** SQLite 3. Используется как основное хранилище данных.
*   **Интерфейс командной строки (CLI):** Реализуется с использованием стандартной библиотеки `argparse`.
*   **Формат данных:** JSON. Все входные и выходные данные должны быть в формате JSON.
*   **Зависимости:** Разработка ведется **без использования внешних библиотек**. Допускается применение только стандартной библиотеки Python ("batteries included").
    *   **Запрещено:** Использование популярных библиотек для анализа данных (Pandas, NumPy), построения конвейеров (Luigi, Airflow), веб-фреймворков и сетевых библиотек.

### 2. Среда выполнения

*   **Операционная система:** Linux. Фреймворк должен быть полностью совместим с Linux-окружением.

### 3. Ограничения и архитектурные принципы

*   **Строгие ограничения окружения:** Фреймворк разрабатывается для среды с фиксированной версией интерпретатора Python и строгими политиками безопасности, запрещающими установку сторонних пакетов.
*   **Отсутствие сетевых взаимодействий:** Приложение не должно занимать сетевые порты или инициировать сетевые соединения.
*   **Совместимость с CPython:** Все алгоритмы обработки данных следует проектировать с учетом будущей оптимизации. В перспективе критичные по производительности участки кода планируется переписать на CPython. Код должен быть совместим по типам данных.
*   **Процесс разработки:**
    *   Все тесты должны разрабатываться и выполняться в отдельной ветке (`develop` или `testing`) на версии Python 3.9.20.
    *   Ветка `main` должна содержать исключительно стабильную, релизную версию кода, очищенную от тестов.

## Архитектура

### 1. Высокоуровневая структура

Фреймворк будет состоять из следующих ключевых компонентов:

*   **CLI (Интерфейс командной строки):**
    *   **Назначение:** Точка входа для пользователя. Отвечает за парсинг команд и их аргументов.
    *   **Технологии:** `argparse`.

*   **Core API (Ядро):**
    *   **Назначение:** Центральный координирующий модуль. Принимает обработанные команды от CLI и вызывает соответствующие сервисы для их выполнения.

*   **Data Loader (Загрузчик данных):**
    *   **Назначение:** Отвечает за чтение и валидацию входных JSON-файлов. Преобразует данные во внутренние структуры данных.

*   **Storage Engine (Хранилище):**
    *   **Назначение:** Слой абстракции для работы с базой данных. Инкапсулирует всю логику SQL-запросов.
    *   **Обязанности:** Запись, чтение, поиск, архивирование и удаление данных.
    *   **Технологии:** `sqlite3`.

*   **Processing Engine (Движок обработки):**
    *   **Назначение:** "Мозг" системы. Реализует ключевую бизнес-логику.
    *   **Обязанности:**
        *   Построение срезов данных на заданный момент времени ("машина времени").
        *   Разрешение коллизий на основе весов доверия `p`.
        *   Выполнение расчетов и агрегаций.

### 2. Схема взаимодействия

```
Пользователь -> CLI -> Core API -> Data Loader  -> Storage Engine
                      |          |                 ^
                      |          -> Processing Engine -|
                      |          |                 |
                      |          <-----------------+
                      |
                      -> Вывод (JSON)
```
