## 2. Добавить временную метку записи в БД (`created_at`)

**Исходная заметка:** добавить новый класс `Cnt` (`cnt_id`, `created_at`) или добавить поле
`created_at` прямо в `Transaction` — проанализировать альтернативы.

**Текущее состояние:** данные физически уже пишутся в БД, но никуда не читаются обратно.
`sqlite_adapter.py` при каждой вставке транзакции создаёт запись в `cnts`:

```python
cur = self._conn.execute("INSERT INTO cnts (created_at) VALUES (julianday('now'))")
```

— однако ни один `SELECT` транзакций (`txn_query`, построение `state`, архивные запросы) не
джойнит `cnts` и не возвращает `created_at`. `Transaction`, `TransactionRecord` и все функции в
`transaction_mapper.py` о этом столбце не знают. `InMemoryAdapter` вообще не считает `created_at` —
там `_next_cnt()` только инкрементирует счётчик, без привязки к времени. Для паритета между
адаптерами (тесты гоняются на обоих) это тоже нужно будет доделать.

**Аргументы за отдельный класс `Cnt`:** соответствует нормализации схемы — `cnts` уже отдельная
таблица.

**Контраргумент (принят):** `cnt_id` и `created_at` связаны 1:1, `created_at` никогда не запрашивается
в отрыве от транзакции — нет сценария "дай мне все cnt без данных транзакции". Отдельная сущность
`Cnt` — лишняя структура без выигрыша в инкапсуляции, только лишний JOIN на каждом чтении.

**Уточнение по месту хранения (по итогам обсуждения):** поле `created_at` переносится прямо в
таблицу `transactions` (денормализация), а не читается через JOIN с `cnts`. Это утяжеляет таблицу
транзакций на одно поле, но избавляет от JOIN на каждый горячий путь чтения — оправдано именно
благодаря связи 1:1.

**Целесообразность:** подтверждён конкретный потребитель — инженерам нужно объяснять, почему
результат сегодня отличается от вчерашнего, когда данные идут в систему по несколько дней с
задержкой. `created_at` — это "когда данные физически долетели", отдельно от `dt` (когда факт
произошёл по бизнес-времени) и `cnt` (порядок вставки). Без этого потребителя поле осело бы мёртвым
грузом — по аналогии с уже известной проблемой: `p`/`description` из конфига источника сейчас
парсятся, но никуда не подставляются (см. известные проблемы проекта).

**Объём работ:**
- `Transaction`/`TransactionRecord` — добавить `created_at: float`. Это frozen dataclass, используется
  по всей кодовой базе и в юнит-тестах, собирающих такие объекты вручную — все construction sites
  придётся обновить.
- `transaction_mapper.py` — `record_to_domain`, `domain_to_record`, `input_to_row` — расширить все три.
- `sqlite_adapter.py::txn_insert` — генерировать timestamp на стороне Python один раз (а не читать
  обратно из БД через `julianday('now')`) и подставлять в обе вставки (`transactions.created_at` и,
  если таблица `cnts` остаётся, туда же).
- `inmemory_adapter.py` — добавить генерацию `created_at` с нуля, её сейчас физически нет.

**Решение:** ✅ Делать. Поле — прямо в `Transaction`/`transactions`, без отдельного класса `Cnt`.

## 3. `fold_state`: порядок сортировки транзакций

**Исходная заметка:** переписать функцию — сортировку сделать не по полю `cnt`, а по полю `dt`,
потому что более ранняя временная метка может прийти в базу данных позже, и текущая реализация
затирает более новые данные более старыми, у которых выше счётчик.

**Найденное во время анализа:** текущее поведение (`cnt`) — не забытый недочёт, а осознанно
зафиксированное решение. В `tests/processing/test_single_source.py` есть тест:

```python
def test_fold_state_winner_decided_by_cnt_not_dt():
    # A misleading dt must not override the cnt-based decision.
    earlier_cnt_later_dt = _txn(cnt=1, val=1, dt=_TS + 100)
    later_cnt_earlier_dt = _txn(cnt=2, val=2, dt=_TS)
    state = fold_state([earlier_cnt_later_dt, later_cnt_earlier_dt])
    assert state[(_SRC, _LB, _ID)] == ValId(2)
```

Название и комментарий показывают, что автор уже рассматривал вопрос "довериться `dt`" и отверг
его — `dt` приходит от источника (внешний вход), `cnt` — системный, назначается хранилищем и не может
быть искажён вызывающей стороной.

**Контраргумент против `dt` (поднятый при анализе):** `dt` не проверяется на правдоподобие —
один неверный timestamp (баг источника, разница часовых зон) навсегда "выигрывает" при фолдинге,
независимо от порядка загрузки, без явной ошибки.

**Контраргумент снят пояснением автора фреймворка:** доверие в модели фреймворка — составное
(`dt` × `p`, вес источника), а не бинарная проверка правдоподобия `dt` самого по себе. Задача "можно
ли доверять этим данным" решается весом источника (`p`), а не подменой `dt` на `cnt`. Проверка `dt`
"на всякий случай" через `cnt` — избыточна и не соответствует архитектуре доверия фреймворка.

**Итоговое, уточнённое правило (принято):**
1. **Внутри одного источника** — приоритет по `dt` (бизнес-время). Это уровень `fold_state` (Level 1).
2. **Между источниками** — приоритет по доверительному весу (`p`/`p_total`) — это Level 2,
   в коде сейчас не реализован (`engine.py`: *"Cross-source, weight-based collision resolution
   (Level 2) is not applied here"*).
3. **Финальный tie-break** (совпали и `dt`, и `p`) — по `cnt`, берём самый свежий. Не по
   `created_at` — при батч-загрузке `created_at` может совпасть у нескольких вставок (одна и та же
   секунда/транзакция), а `cnt` — единственное поле, гарантированно не повторяющееся
   (PK AUTOINCREMENT).

**Расхождение с документацией:** `docs/proposals/DATABASE_DESIGN.md`, раздел "Разрешение
коллизий", описывает другой (более старый) порядок — сравнение `p_total`, при равенстве весов tie-break
по `dt`, без разделения на Level 1/Level 2 и без роли `cnt` как финального tie-breaker'а. Документ
нужно будет обновить под трёхуровневую модель выше, иначе документация и код разойдутся.

**Объём работ:**
- Ключ сортировки в `fold_state` — не просто `dt`, а `(dt, cnt)` (`cnt` — явный tie-break, а не
  случайная стабильность сортировки по входному порядку).
- Развернуть (инвертировать) тесты: `test_fold_state_winner_decided_by_cnt_not_dt`,
  `test_fold_state_later_cnt_overwrites_earlier_for_same_key`,
  `test_fold_state_is_independent_of_input_order`.
- Добавить новый тест: при совпадающем `dt` у двух транзакций одного источника побеждает более
  свежий `cnt`.
- Переписать docstring `fold_state`, который сейчас ссылается на "cnt, the storage-assigned
  insertion order" как на обоснованное правило.
- Обновить `docs/proposals/DATABASE_DESIGN.md` (раздел "Разрешение коллизий").
- Важно: эта правка закрывает только Level 1. Level 2 (приоритет по `p` между источниками) —
  отдельная, более крупная фича, которой в коде пока нет вообще.

**Решение:** ✅ Делать. Сортировка — по `(dt, cnt)`. Механически небольшая правка (одна функция,
~10 строк + тесты), но требовавшая явного согласования модели доверия перед реализацией.

## 4. Метки (`Lb`), специфичные для источника

**Исходная заметка:** добавить в `Lb` ссылку на принадлежность к источнику (`src: SrcId`) —
в текущей реализации две метки с одинаковым именем из разных источников записываются в БД как одна
запись, что в будущем может привести к коллизиям.

**Текущее состояние:** `lbs` — глобальный пул: `lb_id PK, name UNIQUE NOT NULL, description, p`.
`lb_intern(name)` интернирует метку глобально, без привязки к источнику.

**Обнаруженный конфликт с архитектурой:** `docs/proposals/DATABASE_DESIGN.md`, раздел
"Терминология", прямо заявляет:

> Четыре измерения данных: Source → Label → ID → Value

— то есть `Label` документирован как измерение, **независимое** от `Source`. Именно это позволяет
Level 2 (кросс-источниковое сравнение по `p_total`) сопоставлять значения одного показателя из разных
источников по общему `lb_id`. Привязка `Lb` к конкретному `Src` схлопывает два независимых измерения
в одно.

**Аргумент в пользу source-specific меток (принят как решающий):** метка существует только в
контексте конкретного источника, а не сама по себе. Одинаковое имя метки в разных источниках может
означать разные сущности; разные имена в разных источниках могут означать одну и ту же сущность.
Совпадение имени — не гарантия совпадения сущности (и наоборот). Общий пул по имени в этой модели
некорректен по определению, а не просто неудобен.

**Альтернатива, которая была предложена и отклонена:** отдельная таблица override'ов
(`src_label_overrides(src_id, lb_id, p_override, description_override)`), сохраняющая общий пул меток,
но позволяющая переопределять вес/описание точечно для конкретного источника. Отклонена — не
соответствует принятой модели ("метка существует только в контексте источника"), а не только не
решает исходную проблему коллизий имён.

**Обнаруженная техническая проблема — курица и яйцо:**
в `json_loader.py::load()` порядок создания сущностей:

```python
key_lb_r = storage.lb_intern(cfg.key_label)                 # метка создаётся первой
...
src_r = storage.src_get_or_create(cfg.name, key_lb_r.value)  # источник — после, ссылаясь на lb_id метки
```

`Src.key_label` — FK на `lbs(lb_id)`, поэтому key-метка должна существовать до создания источника.
Но если `Lb` требует обязательный `src_id`, key-метку невозможно создать до появления `src_id` — а
`src_id` не появится, пока не создана key-метка. Порядок создания придётся развернуть.

**Пути решения bootstrap-проблемы:**
- Сделать `srcs.key_label` временно nullable: создать `Src` без key_label → создать key-метку с
  `src_id` → `UPDATE srcs SET key_label = ...`.
- Или использовать `PRAGMA defer_foreign_keys = ON` в SQLite в рамках одной транзакции — тогда
  проверка FK откладывается до `COMMIT`, к которому моменту key-метка уже существует. Чище, не
  требует ослаблять `NOT NULL`, но нужно убедиться, что `commit()` в адаптере закрывает транзакцию
  явным `COMMIT`, а не построчным autocommit.

**Важное следствие на будущее (не блокирует текущую правку, но нужно держать в голове):** раз имя
метки больше не гарантирует совпадение сущности между источниками, будущий Level 2 не может
сопоставлять метки разных источников по `lb_id` или по имени — потребуется отдельный явный слой
соответствия меток между источниками (что-то вроде "canonical concept ↔ (src, lb)"), которого сейчас
нет вообще. Level 2 становится дороже, чем в модели с общим пулом меток.

**Объём работ (самый большой из четырёх):**
- Схема: `lbs.src_id INTEGER NOT NULL REFERENCES srcs(src_id)`, `UNIQUE(name)` → `UNIQUE(src_id, name)`.
- `Lb`/`LbRecord`/`lb_mapper.py` — добавить поле `src`.
- `StoragePort.lb_intern(name) -> LbId` → `lb_intern(name, src_id) -> LbId` — breaking change
  интерфейса порта: оба адаптера (`sqlite_adapter.py`, `inmemory_adapter.py`), `json_loader.py`
  (создание key-метки + всех колонок), `api/service.py::_find_lb` (сейчас ищет метку глобально по
  имени — потребует src-контекст).
- `lb_list()`/`lb_get()` — вероятно, нужен опциональный фильтр по `src_id`.
- Тесты: `tests/loader/test_json_loader.py`, `tests/api/test_service.py`, `tests/adapters/*`,
  `tests/persistence/mappers/*` — везде, где метка создаётся/ищется по одному имени, нужно
  протащить `src_id`. Самый широкий blast radius из всех четырёх пунктов.
- `docs/proposals/DATABASE_DESIGN.md` — раздел "Терминология" (формулировка "4 измерения данных"
  перестаёт быть точной), плюс новый пункт в "Принятые архитектурные решения".

**Решение:** ✅ Делать, но отдельной задачей/веткой — не смешивать с пунктами 1–3. Сначала решить
bootstrap-порядок создания `Src`/key-метки, только потом остальная плумбинга.
