# [roadmap] Управление сущностями схемы

> **Статус: rename/merge одной метки — готово (`ds mv`).** Остальное — не реализовано.
> Концепция и граница со «слоем обработки» —
> [`../explanation/entity-curation.md`](../explanation/entity-curation.md). Проектное решение
> принято для этого подмножества (вариант A — переписывание журнала) —
> [`../decisions/0009-entity-curation-rewrite-vs-events.md`](../decisions/0009-entity-curation-rewrite-vs-events.md).
> `ds mv --src SRC --lb LB [--to-src SRC2] --to-lb LB2` переименовывает показатель и/или
> переносит его историю (активную и архивную) в другой источник, с автослиянием, если
> показатель назначения уже накопил часть истории за переходный период — см.
> [`../reference/cli.md#ds-mv`](../reference/cli.md#ds-mv),
> [`../../examples/12-mv-rename/`](../../examples/12-mv-rename/),
> [`../../examples/13-mv-cross-source/`](../../examples/13-mv-cross-source/). Источник
> назначения (`--to-src`) создаётся автоматически, если его ещё нет (как у `ds load`); старая
> запись показателя удаляется из `lbs` сразу по завершении переноса — не остаётся сиротой.

## Задача

Инструментарий инженера для приведения схемы данных в порядок, когда структура «дрейфует»:
показатель переименовали, источник разделили, в `ids` попали дубли из-за форматирования.

| Операция | Над чем | Смысл | Статус |
|---|---|---|---|
| **rename/merge** | `lbs` | переименовать показатель и/или свести две метки в одну (`ds mv`) | **готово** |
| **merge** | `srcs` | слить два источника целиком | не реализовано |
| **merge** | `ids` / `vals` | два id — одна сущность (дубли из-за форматирования); свести транзакции к одному, второй списать | не реализовано |
| **split** | `srcs` / `lbs` / `ids` / `vals` | одна запись конфлатила два понятия; разбить транзакции по предикату | не реализовано |
| **delete** | `srcs` / `lbs` / `ids` / `vals` | убрать осиротевшую запись пула, на которую не ссылается ни одна транзакция (для `ds mv` это уже встроено в саму операцию; для остальных путей сиротства — отдельная задача [`optimization.md`](optimization.md)) | частично |

Решение о смысловом тождестве — снаружи (человек / слой обработки). Ядро только исполняет.

## Открытые вопросы (см. ADR-0009)

Пункт 1 (переписывать журнал vs слой алиасов) решён вариантом A для `lbs` — см. ADR-0009.
Остальное по-прежнему открыто, и решение по `lbs` не обязано переноситься на `srcs`/`ids`/`vals`
без отдельного рассмотрения (например, слияние `ids` требует решить, что делать с источниками,
у которых пересекающиеся диапазоны дат для объединяемых значений — у `lbs` таких коллизий по
конструкции не бывает, см. `UNIQUE(src_id, name)`):

1. ~~Переписывать журнал или слой алиасов~~ — решено (A) для `lbs`, см. ADR-0009.
2. Детект кандидатов ядром (одноимённые метки в непересекающихся диапазонах `dt`, похожие
   имена источников) — или только явная инструкция «слей X и Y». `ds mv` реализует только
   второе (явная инструкция); механический детект кандидатов не рассматривался.
3. Формат задания предиката для `split`.
4. Отдельное логирование операций курации (аудит: кто/когда слил). `ds mv` его не ведёт —
   только обычный stdout-вывод, как у `delete`/`archive`.

## Зависимости и порядок

- Требует стабильной схемы и рабочего пути чтения (`ds get` — реализован,
  [`../reference/cli.md`](../reference/cli.md)) — иначе нечем проверять корректность слияния.
- Самый широкий blast radius для оставшегося (`srcs`/`ids`/`vals`, split): схема (`UNIQUE`,
  FK), порт, оба адаптера, весь периметр тестов. `ds mv` (`lbs` rename/merge) был у́же —
  один новый примитив порта (`lb_merge`), без изменений схемы.
- Делать оставшееся отдельной веткой, не смешивая с другими пунктами roadmap.

## Затрагиваемые инварианты

- Append-only журнал ([`../explanation/event-sourcing.md`](../explanation/event-sourcing.md)).
- `transactions_archive` — операция должна одинаково работать по обеим таблицам (или явно
  запрещать курацию при непустом архиве до отдельного решения).
- Осиротевшие записи `vals`/`ids` после merge — чистятся в рамках
  [`optimization.md`](optimization.md).
