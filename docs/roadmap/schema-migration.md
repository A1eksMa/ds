# [roadmap] Миграции схемы

> **Статус: не реализовано.** Сейчас `SQLiteAdapter` создаёт схему через
> `CREATE TABLE IF NOT EXISTS` и не умеет менять существующую.

## Задача

Когда меняется структура самого ядра (новое поле в `transactions`, новый `UNIQUE`, новая
таблица), нужен управляемый способ привести существующие БД к новой схеме — без потери
данных и воспроизводимо.

## Что проработать

- **Обнаружение версии схемы.** Отдельного `SCHEMA_VERSION` нет ([ADR-0008](../decisions/0008-no-separate-schema-versioning.md))
  — привязка к тегу `ds`. Нужен ли служебный ключ в БД (`PRAGMA user_version` или таблица
  `meta`), чтобы миграция знала, откуда стартует.
- **Форма миграции.** Набор SQL-скриптов `NNNN_description.sql` + раннер на stdlib, или
  Python-функции `migrate_0004_to_0005(conn)`. Только stdlib ([ADR-0001](../decisions/0001-stdlib-only-sqlite-offline.md)).
- **Специфика SQLite.** Ограниченный `ALTER TABLE` (нельзя менять/удалять колонку, менять
  ограничения) → паттерн «create new table → copy → drop → rename», аккуратно с FK и
  `transactions_archive` (структуры должны оставаться идентичными).
- **Атомарность и откат.** Миграция под одной транзакцией; бэкап файла БД перед запуском.
- **Идемпотентность / повторный запуск.**
- **Пересчёт производных.** Если появится таблица `state` — миграция должна её (пере)собрать.

## Исторические примеры (что уже пришлось бы мигрировать)

- 0.5.0a1: `transactions.created_at` (новое поле), `lbs` → `UNIQUE(src_id, name)` +
  `lbs.src_id NOT NULL`, `srcs.key_label` стал nullable. Пока это ложилось «в чистую» на
  тестовые БД — на рабочих данных понадобился бы миграционный скрипт.
