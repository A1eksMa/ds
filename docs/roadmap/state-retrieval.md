# [roadmap] Выдача состояния источника (`ds get`)

> **Статус: не реализовано.** Команда `ds get` и весь путь чтения (`build_state`,
> `build_export`, `fold_state`) были в 0.4.0a1 и сняты в 0.5.0a1 при откате к ядру: старая
> логика опиралась на прежнюю схему (`cnt`-only коллизии, метки без привязки к источнику).
> Возможны ещё пара изменений схемы до того, как это будет переписано.
>
> Документ ниже — **описание реализации 0.4.0a1**, сохранённое как целевая спецификация:
> внешний интерфейс (`--src`/`--lb`/`--dt`/`--archive`, формат `{metadata, data}`, «файл не
> создаётся при ошибке») переносится как есть; внутренности переписываются под текущую схему.
> Правило свёртки Level 1 при переписывании — по `(dt, cnt)`, а не по `cnt`
> (см. [`../decisions/0006-fold-order-dt-cnt.md`](../decisions/0006-fold-order-dt-cnt.md),
> [`single-source-fold.md`](single-source-fold.md)).
>
> **В scope ядра** ([`../decisions/0007-scope-freeze-storage-core.md`](../decisions/0007-scope-freeze-storage-core.md)):
> внешним системам нужно получать состояние источника на заданное время по запросу. Выдаётся
> результат **Level 1** (по записи на `(src, lb, id)`); кросс-источниковое разрешение по `p`
> (Level 2) — вне ядра. Ссылки на `src/api/service.py:*` и `src/processing/*` ниже — это пути
> **удалённого** кода 0.4.0a1, оставлены для ориентира.

## (0.4.0a1) Выгрузка состояния: пошаговая инструкция

Этот документ описывает команду `ds get` — выгрузку текущего (или прошлого) состояния данных
в JSON-файл. Все примеры не абстрактные: получены реальным прогоном команд из этого репозитория
(`SQLiteAdapter`), продолжают тот же сквозной пример, что и `docs/guides/loading-data.md` (те же
`sources/CRM/source.json`, `batch_2024-01.json`, `batch_2024-02.json`).

---

## 0. Что нужно, чтобы `ds get` вообще что-то вернул

Ничего особенного — данные должны быть уже загружены командой `ds load` (см. `docs/loader.md`).
Отдельного шага "построить состояние" делать не нужно: `ds get` строит его на лету при каждом
вызове (подробнее — раздел 2).

---

## 1. Запуск

```bash
ds --db data.db get state.json
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `--db` | нет (по умолчанию `data.db`) | путь к файлу SQLite — тот же, что использовался при `load` |
| `out` | да | путь к выходному JSON-файлу; перезаписывается, если уже существует |
| `--src` | нет | фильтр по имени источника (например, `CRM`); без фильтра — все источники сразу |
| `--lb` | нет | фильтр по имени показателя (например, `email`); без фильтра — все показатели |
| `--dt` | нет (по умолчанию — текущий момент, без среза) | unix-timestamp: "машина времени" — состояние **на этот момент**, а не текущее |
| `--archive` | нет (по умолчанию выключено) | включить в выборку заархивированные транзакции (`transactions_archive`) |

Фильтра по конкретному объекту (`--id`) **нет** — сознательное ограничение: у объектов нет
операции обратного поиска "найти id_id по значению, не создавая его", а фильтрация по
несуществующему id создала бы в БД мусорную запись как побочный эффект. Если нужен объект
целиком — фильтруй результат уже в самом JSON после выгрузки.

---

## 2. Что происходит внутри при выгрузке (по шагам)

На примере `ds --db data.db get state.json` после обеих загрузок из `docs/loader.md`:

1. **Резолв фильтров по имени** (`src/api/service.py:39,49` — `_find_src`/`_find_lb`): если
   передан `--src`/`--lb`, имя ищется в `srcs`/`lbs` через `src_list()`/`lb_list()` — **без
   создания** записи, если имя не найдено (в отличие от `load`, где источник/метка создаются
   автоматически). Если имя не найдено — сразу `NotFound`, выгрузка не начинается, файл не
   создаётся.
2. **Построение state** (`src/processing/engine.py:12` — `build_state()`): формируется и
   выполняется SQL-запрос к `transactions` (или `transactions_full`, если `--archive`) с
   `WHERE src = ? AND lb = ? AND dt <= ?` (только для переданных фильтров), `ORDER BY cnt`.
   Возвращается **весь** подходящий список транзакций — полное сканирование, без каких-либо
   индексов/чекпоинтов под этот конкретный запрос.
3. **Свёртка в state** (`src/processing/single_source.py:11` — `fold_state()`): список
   транзакций сворачивается в Python в словарь `{(src_id, lb_id, id_id): val_id}` — последняя по
   `cnt` запись на ключ побеждает. `DELETE` остаётся в словаре как `val_id = 0`.
4. **Резолв числовых id обратно в строки** (`src/api/service.py:59` — `_state_to_records()`):
   для каждой записи `state` числовые `src_id`/`lb_id`/`id_id`/`val_id` превращаются обратно в
   имена/значения через `src_get()`/`lb_get()`/`id_get()`/`val_get()` (с кешированием по
   `src_id`/`lb_id` внутри одного вызова, чтобы не резолвить одно и то же имя источника
   многократно). `val_id = 0` превращается в `val: null` (символ удаления), а не в вызов
   `val_get()` — такого `val_id` в таблице `vals` не существует.
5. **Сборка `{metadata, data}`** (`src/api/service.py:96` — `build_export()`): `data` — список
   записей `{"src", "lb", "id", "val"}`, отсортированный по числовым id для детерминированного
   порядка; `metadata` — `generated_at` (время вызова CLI), `until_dt`, `include_archive`,
   `src`, `lb` (то, что передано в фильтрах, или `null`), `count`.
6. **Запись файла** (`src/api/service.py:143` — `export_state_file()`): `json.dumps(..., indent=2,
   ensure_ascii=False)` пишется в файл. Если на любом из предыдущих шагов была ошибка — файл
   **не создаётся вообще** (ни частично, ни пустой).

Никакого сохранения результата обратно в БД не происходит — ни таблицы `state`, ни каких-либо
чекпоинтов в текущей реализации нет. Каждый вызов `ds get` — это independent полный пересчёт
(см. раздел 5).

## 3. Символический пример целиком

Продолжение примера из `docs/loader.md` — после обеих загрузок (`batch_2024-01.json` с
`--dt 1704067200`, `batch_2024-02.json` с `--dt 1706745600`) в БД лежит 8 транзакций по 4
объектам источника `CRM`.

### Команда

```bash
ds --db data.db get state.json
# exported 7 record(s) to state.json
```

### Реальное содержимое `state.json`

```json
{
  "metadata": {
    "generated_at": 1783561080.5254118,
    "until_dt": null,
    "include_archive": false,
    "src": null,
    "lb": null,
    "count": 7
  },
  "data": [
    {"src": "CRM", "lb": "email", "id": "101", "val": "alice@example.com"},
    {"src": "CRM", "lb": "email", "id": "102", "val": "bob.new@example.com"},
    {"src": "CRM", "lb": "email", "id": "103", "val": "carol@example.com"},
    {"src": "CRM", "lb": "email", "id": "104", "val": "dave@example.com"},
    {"src": "CRM", "lb": "phone", "id": "101", "val": "+7-900-000-0001"},
    {"src": "CRM", "lb": "phone", "id": "102", "val": "+7-900-000-0002"},
    {"src": "CRM", "lb": "phone", "id": "103", "val": null}
  ]
}
```

Обрати внимание:
- `email` для `102` — `bob.new@example.com`, а не `bob@example.com` из первого батча: второй
  батч (`POST`, более поздний `cnt`) победил, как и должно быть по правилу "последняя запись
  выигрывает".
- `phone` для `103` — `null`: это `DELETE` из первого батча (в исходных данных `phone` для
  клиента 103 был `null`), объект остался в выгрузке явной записью, а не пропал молча.
- `104` не имеет `phone` вообще — в `state` для него просто нет ключа `(CRM, phone, 104)`,
  потому что такой пары `(источник, метка, id)` не было ни в одной транзакции. Это не то же
  самое, что `DELETE`.

### "Машина времени": срез на момент первого батча

```bash
ds --db data.db get --dt 1704067200 state_jan.json
# exported 6 record(s) to state_jan.json
```

```json
{
  "metadata": {
    "generated_at": 1783561088.464212,
    "until_dt": 1704067200.0,
    "include_archive": false,
    "src": null,
    "lb": null,
    "count": 6
  },
  "data": [
    {"src": "CRM", "lb": "email", "id": "101", "val": "alice@example.com"},
    {"src": "CRM", "lb": "email", "id": "102", "val": "bob@example.com"},
    {"src": "CRM", "lb": "email", "id": "103", "val": "carol@example.com"},
    {"src": "CRM", "lb": "phone", "id": "101", "val": "+7-900-000-0001"},
    {"src": "CRM", "lb": "phone", "id": "102", "val": "+7-900-000-0002"},
    {"src": "CRM", "lb": "phone", "id": "103", "val": null}
  ]
}
```

Видно: `102` всё ещё `bob@example.com` (второй батч ещё не наступил по времени среза), и `104`
вообще отсутствует (его batch пришёл только `--dt 1706745600`, позже среза).

### Фильтр по показателю (по всем источникам сразу)

```bash
ds --db data.db get --lb email state_email.json
# exported 4 record(s) to state_email.json
```

`data` содержит только 4 записи с `"lb": "email"` (все `phone` отфильтрованы), `metadata.lb`
выставлен в `"email"`.

### Неизвестное имя источника — явная ошибка, файл не создаётся

```bash
ds --db data.db get --src does-not-exist state_bad.json
# error: Src not found: does-not-exist
echo $?
# 1
```

`state_bad.json` в этом случае не появляется на диске вообще.

## 4. Архив: `--archive`

Архивирование (`txn_archive`) реализовано на уровне хранилища, но **не выведено в CLI** (то же
ограничение, что описано в `docs/loader.md`, раздел 5). Чтобы продемонстрировать разницу,
заархивируем транзакции первого батча напрямую через Python:

```python
from src.adapters.sqlite_adapter import SQLiteAdapter
db = SQLiteAdapter("data.db")
db.txn_archive(until_dt=1704067200)   # -> Ok(6): все 6 транзакций первого батча ушли в архив
```

После этого:

```bash
ds --db data.db get state_no_archive.json
# exported 2 record(s) to state_no_archive.json
```

Осталось только 2 записи — `email` для `102` и `104` (обе из второго, неархивированного батча).
`101` и `103` **пропали из выгрузки полностью**, потому что все их транзакции уехали в
`transactions_archive`, а `get` по умолчанию читает только `transactions`.

```bash
ds --db data.db get --archive state_with_archive.json
# exported 7 record(s) to state_with_archive.json
```

С `--archive` (читает `transactions_full = transactions UNION ALL transactions_archive`) —
снова все 7 записей, как до архивирования. Архивирование не теряет данные, только "прячет" их
из выгрузки по умолчанию.

## 5. На что обратить внимание при работе с реальными данными

- **Каждый вызов `ds get` — это полный пересчёт с нуля**, а не чтение готового снэпшота: SQL
  full/filtered scan журнала + свёртка в Python при каждом запуске (см. раздел 2, шаги 2-3).
  Персистентного снэпшота (таблицы `state` или файлов чекпоинтов, как задумано в
  `docs/proposals/DATABASE_DESIGN.md`) не существует — ничего не кешируется между вызовами.
- **Кросс-источниковое разрешение коллизий по весам доверия `p` (Level 2) не реализовано.**
  Если не передать `--src`, а данные по одному и тому же `(lb, id)` есть в нескольких
  источниках, `data` будет содержать **несколько отдельных записей** — по одной на источник, с
  одинаковыми `lb`/`id`, но разными `src` и потенциально разными `val`. Выбора "чьё значение
  главнее" фреймворк за тебя не делает.
- **Формат частично отличается от `docs/proposals/DATABASE_DESIGN.md`.** В доке для "формата
  выгрузки" (в противовес "внутреннему снэпшоту") заложено `{metadata, data, configs}` — с
  конфигами источников/показателей внутри файла. Текущая реализация выгружает только
  `{metadata, data}` (формат "внутреннего снэпшота" по той же доке) — `configs` нет.
- **Нет фильтра по конкретному id** — см. раздел 1. Если нужен один объект, фильтруй сам JSON
  после выгрузки, либо (что надёжнее для больших объёмов) добавь `--id` отдельно, если это
  регулярно понадобится — сейчас сознательно не сделано, чтобы не плодить read-путь с побочным
  эффектом создания записи в `ids` под несуществующее значение.
- **Файл не создаётся при ошибке** — ни частично, ни пустым (см. раздел 3, пример с неизвестным
  источником). Если `ds get` вернул код `1`, можно быть уверенным, что старого файла по тому же
  пути (если он был) не тронули — запись происходит одним вызовом `path.write_text(...)` в
  самом конце, после того как весь экспорт уже полностью собран в памяти.
