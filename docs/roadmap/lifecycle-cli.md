# [roadmap] Жизненный цикл данных в CLI

> **Статус: `delete` — готово.** `ds delete --src NAME [--lb NAME] [--yes]` реализован
> (`src/service/delete.py` + `StoragePort.txn_delete`), см.
> [`../reference/cli.md#ds-delete`](../reference/cli.md#ds-delete),
> [`../../examples/05-delete-label/`](../../examples/05-delete-label/). Заодно исправлен
> баг обоих адаптеров: `txn_delete` возвращал число удалённых строк только из активной
> таблицы, молча занижая счётчик, когда совпадающие строки были ещё и в архиве.
>
> **`archive`/`restore` — не сделаны.** `txn_archive(until_dt)` в порту есть, но принимает
> только глобальный срез по дате, без фильтра по источнику/показателю — см. открытый вопрос
> ниже. Пока — только из Python,
> см. [`../guides/archiving-via-python.md`](../guides/archiving-via-python.md).

## Что нужно (осталось)

| Команда (черновой вид) | Метод порта | Смысл |
|---|---|---|
| `ds archive --src NAME [--lb NAME] [--until-dt TS]` | `txn_archive` — **нужно расширить** фильтром `src_id`/`lb_id` (сейчас только `until_dt`, глобально) | перенести транзакции (опц. одного источника/показателя, опц. до даты) в `transactions_archive` |
| `ds restore --until-dt TS` (?) | — | обратный перенос из архива — метода пока нет |

Флаги задуманы совместимыми с уже реализованным `delete` — `--src`/`--lb` тот же смысл и то
же резолв имён (`src/service/delete.py::resolve_target` можно переиспользовать для `archive`
как есть, счётчик-превью — `count_matching`), `--yes` та же семантика подтверждения. Следующий
шаг, о котором думаем вместе с пользователем, шире, чем просто `archive`/`restore`: сюда же
ложится автоматическое архивирование по правилу (устаревшие/неиспользуемые показатели или
источники) и дедупликация (перенос дублей в архив либо `delete`) — они должны опираться на
тот же `--src`/`--lb`-интерфейс, а не изобретать свой.

## Вопросы к проработке

- Расширение `txn_archive` фильтром `src_id`/`lb_id` (аналогично `txn_delete`) — нужно решить
  порядок аргументов/умолчаний, не ломая текущий вызов с одним `until_dt`.
- Нужна ли операция `restore` (обратный перенос из архива) и `purge` осиротевших записей
  пулов — пересекается с [`optimization.md`](optimization.md).
- Правило автоматического архивирования (по давности? по правилу «не используется в
  последних N выгрузках»?) и дедупликации (что считать дублем — совпадение `lb`+`id`+`val` при
  разных `src`? схема-дрейф, см. [`entity-curation.md`](entity-curation.md)?) — оба ещё не
  сформулированы, только обозначены пользователем как следующий приоритет.
