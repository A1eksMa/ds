# Формат конфигурации источника (`source.json`)

Как в коде на 0.6.0a1 (`src/config/loader.py`, `src/config/models.py`, `src/config/validator.py`).
Исходно этот файл был заплаткой к `PROJECT_STRUCTURE.md` (там предполагался YAML — реализация
использует JSON, потому что `PyYAML` — внешняя зависимость; см.
[`../explanation/constraints.md`](../explanation/constraints.md)).

**Не только для `ds`.** `source.json` — общий, читаемый напрямую файл-конфиг источника для
всего стека, а не приватный формат ядра: `ds load` использует его весь (список показателей,
`archive`); `ds-loader` при публикации читает те же `type`/`publish` из того же файла (ещё не
реализовано на его стороне); `type` рассчитан на то, чтобы `ds-webui` при добавлении «показателя
источника» подставляла его как тип сущности (тоже задел на будущее — сам `ds` этим не
занимается). Персистить эти три поля в БД **не нужно** — они не про журнал транзакций, а про
декларацию схемы источника, и каждый инструмент читает их из файла напрямую.

## Расположение

Источник описывается папкой с обязательным файлом `source.json`. Путь к этой папке —
позиционный аргумент `ds load <source_dir> ...`. Жёсткой раскладки `data/` в коде нет:
папку источника кладёшь куда удобно, БД задаётся через `--db` (по умолчанию `data.db`).

```
sources/
└── CRM/
    └── source.json          единственный файл конфигурации источника
```

(До 0.6.0a1 существовал ещё каталог `labels/<name>/config.json` — читался, но ни на что не
влиял, см. changelog. Убран: один показатель — одна запись в `labels` ниже, а не два
параллельных, несинхронных механизма.)

## `source.json`

Обязательные поля: `name`, `key_label`.

```json
{
  "name": "CRM",
  "key_label": "customer_id",
  "p": 0.9,
  "description": "CRM-система",
  "labels": [
    { "name": "email", "type": "text" },
    { "name": "revenue", "type": "number" },
    { "name": "internal_note", "type": "text", "archive": true },
    { "name": "legacy_flag", "type": "bool", "publish": false }
  ]
}
```

| Поле | Тип | Обяз. | По умолч. | Что делает на практике |
|---|---|---|---|---|
| `name` | string | да | — | имя источника; под ним он создаётся в `srcs` |
| `key_label` | string | да | — | имя столбца во входных данных с уникальным `id` объекта |
| `p` | float | нет | `0.5` | **парсится и проверяется на диапазон `[0.0, 1.0]`, но до БД не доходит** — `load` не передаёт его в `src_get_or_create`. Реальный вес источника останется `0.5`. См. [`../explanation/trust-weights.md`](../explanation/trust-weights.md). |
| `description` | string | нет | `null` | парсится, загрузчиком никуда не используется |
| `labels` | array | нет | `[]` | инвентарь показателей источника, см. ниже |

## `labels[]` — инвентарь показателей

Каждый элемент описывает один показатель:

```json
{
  "name": "internal_note",
  "type": "text",
  "archive": true,
  "publish": false,
  "p": 0.8,
  "description": "Служебная заметка, не для витрины"
}
```

| Поле | Тип | Обяз. | По умолч. | Смысл |
|---|---|---|---|---|
| `name` | string | да | — | имя показателя (как столбец во входных данных) |
| `type` | string | нет | `"text"` | `"text"` \| `"number"` \| `"date"` \| `"bool"` — тот же словарь, что у `view.entities[].type` в пресете `ds-webui`. Невалидное значение → ошибка загрузки. **Справочное**: `ds` его нигде не парсит и не проверяет данные на соответствие, только хранит и передаёт дальше. |
| `archive` | bool | нет | `false` | **единственное поле из этой тройки, на которое реагирует сам `ds`**: при `ds load` транзакции этого показателя пишутся сразу в `transactions_archive`, минуя активную таблицу (см. ниже). |
| `publish` | bool | нет | `true` | предназначено для стадии `publish` поллера `ds-loader` — какие показатели включать при перестроении витрины/манифеста. `ds` это поле не читает и не проверяет, кроме синтаксиса. |
| `p` | float | нет | `0.5` | вес доверия показателя (см. [`../explanation/trust-weights.md`](../explanation/trust-weights.md)); как и `Source.p`, парсится, но пока не доходит до `lbs.p` в БД (та же незавершённость, что у `Source.p`) |
| `description` | string | нет | `null` | справочно, не используется загрузчиком |

Показатель, которого нет в `labels` (встретился в файле данных явочным порядком), продолжает
регистрироваться на лету, как и раньше — `labels` обогащает схему, а не ограничивает её жёстким
списком допустимых полей. Опечатка в `type` (значение не из четырёх допустимых) — ошибка
`ds load`, аналогично тому, как `p` вне `[0.0, 1.0]` уже проверяется при парсинге.

### `archive: true` — что происходит физически

`ds load` вставляет каждую ячейку такого показателя через `StoragePort.txn_insert(txn,
archived=True)` — прямиком в `transactions_archive`, не в `transactions`, без промежуточного
`ds archive`/`ds delete`. Определение `PATCH` vs `POST` при этом не ломается: история читается
через `txn_last_values`, которая и так видит активные и архивные записи вместе. Объявлять
`archive` для ключевого показателя (`key_label`) бессмысленно, но безвредно — у ключа
собственных транзакций не бывает (см. [`get-output-format.md`](get-output-format.md)), поле
просто ни на что не повлияет.

## Минимальная рабочая конфигурация

```
sources/CRM/source.json  →  {"name": "CRM", "key_label": "customer_id"}
```

```bash
ds --db data.db load sources/CRM batch_2024-01.json --dt 1704067200
```

Формат самого файла данных — [`data-format.md`](data-format.md). Разбор загрузки —
[`../guides/loading-data.md`](../guides/loading-data.md).
