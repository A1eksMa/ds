# CLI `ds` (как в коде)

Точка входа — `src/cli/commands.py :: main` (`pyproject.toml` → `[project.scripts] ds`).
Реализована на `argparse`, только stdlib.

Подкоманды: `load`, `upload`, `update`, `get`, `delete`, `archive`, `compact`.

## Общий вид

```
ds [--db PATH] <command> ...
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `--db PATH` | нет | путь к файлу SQLite. По умолчанию `data.db` в текущей директории. Создаётся автоматически со схемой, если файла нет. |
| `<command>` | да | `load`, `upload`, `update`, `get`, `delete`, `archive` или `compact` |

## `ds load`

```
ds [--db PATH] load <source_dir> <data_file> [--dt TS]
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `source_dir` | да | папка с `source.json` (см. [`config-format.md`](config-format.md)) |
| `data_file` | да | путь к файлу колоночного JSON (см. [`data-format.md`](data-format.md)) |
| `--dt TS` | нет | Unix-timestamp «с какого момента данные актуальны» (бизнес-время). По умолчанию — `time.time()` в момент запуска. |

Флага выбора типа операции (`--act`) **нет** — `act` определяется автоматически по ячейке.
Показатели, отмеченные `"archive": true` в `labels[]` источника, при этом грузятся прямиком в
архив — см. [`config-format.md`](config-format.md#archive-true--что-происходит-физически).

### Вывод

- Успех: `loaded <N> transaction(s)` в stdout, код возврата `0`.
- Ошибка: `error: <сообщение>` в stderr, код возврата `1`. Подробнее — [`errors.md`](errors.md).

### Пример

```bash
ds --db data.db load sources/CRM batch_2024-01.json --dt 1704067200
# loaded 6 transaction(s)
```

Полный разбор с реальным выводом и содержимым таблиц — [`../guides/loading-data.md`](../guides/loading-data.md).
Запускаемые примеры — [`../../examples/`](../../examples/).

## `ds upload`

То же самое, что `ds load`, но со строгой предварительной проверкой — загружает файл целиком
и как есть **только** если он полностью укладывается в уже известную схему; при малейшем
несоответствии не грузит вообще ничего (ни одной строки). Задумано для случаев, когда
уверенности в происхождении файла нет — например, файл выбран интуитивно и есть риск, что он
на самом деле не от того источника. Реализация — `src/service/upload.py::validate_known_schema`
(проверка) + `src/service/load.py::load` (сама загрузка, без изменений, как у `ds load`).

```
ds [--db PATH] upload <source_dir> <data_file> [--dt TS]
```

Аргументы — как у `ds load`. Разница только в проверке, выполняемой ДО загрузки:

- **Нет новых показателей.** Каждый столбец файла (кроме `key_label`) должен быть уже
  известен — либо когда-то раньше загружался для этого источника (есть в пуле `lbs`), либо
  заранее объявлен в `labels[]` `source.json` (это единственный способ, которым `ds upload`
  вообще может загрузить данные для **совсем нового** источника — без объявленных `labels[]`
  первая же загрузка будет отвергнута целиком, потому что известных показателей ещё нет).
  Неизвестный столбец — ошибка, ничего не грузится.
- **Значения проходят по объявленному типу.** Тип берётся из `labels[].type` в `source.json`;
  показатель, известный только по факту прошлой загрузки (не объявлен в файле), типа не имеет
  и трактуется как `text` — без ограничений. `null` (`DELETE`) валиден при любом объявленном
  типе. Проверка типов — упрощённая и настроенная на строгость, а не на богатство разбора (ср.
  типизацию сущностей в `ds-webui`, которая как раз старается распознать побольше форматов):
  `number` — `float()`; `date` — ISO 8601 (`datetime.fromisoformat`) либо unix-время (9–13
  цифр); `bool` — только `true/false/1/0/yes/no/y/n`, регистронезависимо.
- Проверяется **весь** файл целиком **до** какой-либо загрузки — при первом же несовпадении
  (неизвестный столбец или непарсящееся значение) не загружается ни одна строка, даже если
  остальные столбцы/строки были бы в порядке.

### Вывод

- Успех: `uploaded <N> transaction(s)` в stdout, код `0`.
- Ошибка (неизвестный показатель, непарсящееся значение, как у `ds load`): `error: <текст>` в
  stderr, код `1`.

### Пример

```bash
ds --db data.db upload sources/CRM batch_suspicious.json --dt 1704067200
# error: unknown label 'weird_field' -- not previously loaded for 'CRM' and not declared in its source.json
```

## `ds update`

Синхронизирует инвентарь `labels[]` в `source.json` с тем, что реально есть в БД **сейчас** —
пишет файл заново. Реализация — `src/service/config_sync.py::sync_labels` (вычисляет разницу)
+ `src/config/writer.py::write_source` (перезаписывает файл).

```
ds [--db PATH] update <source_dir>
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `source_dir` | да | та же папка, что у `ds load` — читается и перезаписывается её `source.json`. |

Правила:

- Показатель, у которого есть хоть одна транзакция (активная или архивная), но он не объявлен
  в `labels[]`, — **добавляется** как есть (`{"name": ...}`, тип `"text"` по умолчанию — `ds` не
  умеет угадывать реальный тип, только человек может его проставить постфактум).
- Объявленный показатель, у которого **не осталось ни одной транзакции нигде** (например, после
  `ds delete --lb ... --yes`), — **убирается** из `labels[]`.
- Показатель, у которого данные всё ещё есть (хотя бы в архиве), — его запись в конфиге **не
  трогается** (`type`/`archive`/`publish`/`p`/`description` сохраняются как есть).
- `key_label` исключён из удаления всегда — у ключевого показателя никогда не бывает
  собственных транзакций (см. [`get-output-format.md`](get-output-format.md)), поэтому формально
  он «без данных» всегда; без этого исключения `update` стирал бы его из `labels[]` при каждом
  запуске.
- Источник, которого ещё нет в БД (`ds load` по нему ни разу не запускался), — ошибка, а не
  тихая зачистка всего файла: `source.json` может быть подготовлен заранее.

Файл перезаписывается целиком в каноническом виде (поля со значением по умолчанию опускаются
для краткости) — при ручном форматировании ожидай, что стиль/порядок ключей после `update`
изменится.

### Вывод

- Есть изменения: `added: <имена через запятую>` и/или `removed: <имена через запятую>` в
  stdout, код `0`.
- Изменений нет: `source.json already up to date`, код `0`.
- Ошибка (источник не найден в БД, файл/JSON битые): `error: <текст>` в stderr, код `1`.

### Пример

```bash
ds --db data.db update sources/CRM
# added: email, phone
# removed: old_junk_field
```

## `ds get`

Свёртка журнала в состояние источника (Level 1) и выгрузка в JSON. Реализация —
`src/service/get.py`. Формат выходного документа — [`get-output-format.md`](get-output-format.md).

```
ds [--db PATH] get [--out DIR] [--src NAME]... [--lb NAME]... [--dt TS] [--preset FILE] [--archive]
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `--out DIR` | нет | директория; пишет `<Source>.json` на каждый источник. Без `--out` — печатает в stdout. |
| `--src NAME` | нет | имя источника; флаг повторяемый. По умолчанию — все источники. Неизвестное имя → ошибка (запись не создаётся). |
| `--lb NAME` | нет | имя показателя; флаг повторяемый. По умолчанию — все показатели источника. Неизвестное имя → ошибка. Ключевой показатель в списке игнорируется (он всегда колонка-ключ). |
| `--dt TS` | нет | Unix-timestamp: срез «на этот момент» (машина времени). По умолчанию — текущее время. |
| `--preset FILE` | нет | JSON-пресет; параметры берутся из его секции `query` (см. [get-output-format.md](get-output-format.md#пресет)). Явные флаги перекрывают значения пресета. |
| `--archive` | нет | включить в свёртку заархивированные транзакции (`transactions_full`). Только включает; выключить флагом нельзя. |

### Вывод

- `--out DIR`: пишет файлы, печатает `wrote <N> file(s) to <DIR>`, код `0`.
- Без `--out`, один источник: печатает `{meta, data}` этого источника.
- Без `--out`, несколько источников: печатает объект `{"<Source>": {meta, data}, ...}`.
- Ошибка (`--src`/`--lb` не найден, битый пресет, ввод-вывод): `error: <текст>` в stderr, код `1`.

### Примеры

```bash
ds --db data.db get --dt 1706745600                 # все источники, все показатели, на дату — в stdout
ds --db data.db get --src CRM --lb email --lb phone # только CRM, два показателя
ds --db data.db get --out data/ --preset base.json  # по файлу на источник, параметры из пресета
```

Разбор — [`../guides/reading-state-via-sql.md`](../guides/reading-state-via-sql.md) (альтернатива через SQL),
[`../explanation/single-source-fold.md`](../explanation/single-source-fold.md) (правило свёртки),
пример [`../../examples/04-get/`](../../examples/04-get/).

**Манифест `ds get` не пишет.** Индекс над набором файлов + `.js`-обёртка под `file://` —
задача поллера/потребителя, не ядра (см. [get-output-format.md](get-output-format.md#чего-get-не-делает)).

## `ds delete` / `ds archive`

Две стороны одной операции — **что затронуть** задаётся абсолютно одинаковым набором флагов
(общий резолв — `src/service/selector.py`), различается только конечное действие:

- **`ds delete`** — физически удаляет транзакции — **навсегда**, из обеих таблиц
  (`transactions` и `transactions_archive`). Не путать с `DELETE`-актом (`val: null`, см.
  [`../explanation/delete-semantics.md`](../explanation/delete-semantics.md)) — тот оставляет
  запись в журнале как отметку «удалено», `ds delete` стирает историю совсем.
- **`ds archive`** — переносит подходящие **активные** транзакции в `transactions_archive`
  (`StoragePort.txn_archive`) — обратимо в том смысле, что данные никуда не пропадают, только
  перестают попадать в `ds get` по умолчанию (нужен `--archive`).

```
ds [--db PATH] delete  --src NAME [СЕЛЕКТОР] [--yes]
ds [--db PATH] archive --src NAME [СЕЛЕКТОР] [--yes]
```

### Селектор — что затронуть

| Флаг | Повторяемый | Смысл |
|---|---|---|
| `--src NAME` | нет | источник. **Обязателен всегда** (даже для чисто временного отбора) — осознанно, чтобы одна команда не могла задеть всю БД разом. Неизвестное имя → ошибка, запись не создаётся (как и `--src`/`--lb` в `ds get`). |
| `--lb NAME` | да | показатель(и); без него — все показатели источника. Неизвестное имя → ошибка. |
| `--id VALUE` | да | ключ(и) (значения `key_label`); без него — все ключи. Неизвестное значение → ошибка (не резолвится в новую запись пула `ids`, в отличие от `ds load`). Взаимоисключим с `--where`. |
| `--where LB=VALUE` | нет | альтернатива `--id`: ключи вычисляются сверткой (Level 1, активные + архивные транзакции, «на сейчас») показателя `LB` — берутся те, у кого текущее значение равно `VALUE`. Затрагивает **все** показатели найденных ключей, если `--lb` не сужен отдельно. Неизвестный `LB` → ошибка; отбор в ноль ключей — не ошибка, просто нечего трогать. |
| `--cnt N` | да | конкретная запись по номеру счётчика. **Самостоятельный режим** — не сочетается с `--lb`/`--id`/`--where`/`--dt-*`/`--created-*` (ошибка при попытке смешать). Значение `cnt`, не принадлежащее указанному `--src`, → ошибка. |
| `--dt-from TS` / `--dt-until TS` | нет | диапазон **бизнес-времени** записи (`dt`) — период, к которому относятся данные. |
| `--created-from TS` / `--created-until TS` | нет | диапазон **времени физической загрузки** в БД (`created_at`) — когда запись реально попала в журнал, независимо от того, к какому `dt` она относится. |
| `--yes` | нет | не спрашивать подтверждение. |

Всё, кроме `--cnt`, комбинируется через И (источник ∧ показатели ∧ ключи ∧ диапазоны дат) —
как фильтры `txn_query`. Перед операцией всегда считается точное число подходящих транзакций
(активных + архивных) — для показа в вопросе и для итогового сообщения; при `0` — само действие
не выполняется, вопрос не задаётся. Без `--yes` — интерактивный вопрос `Delete/Archive <N>
transaction(s) for <описание отбора> (active + archived)? [y/N]`; недоступный/закрытый stdin
трактуется как отказ (по умолчанию безопаснее ничего не сделать, чем сделать по ошибке).

### Вывод

- Успех: `deleted <N> transaction(s)` / `archived <N> transaction(s)` в stdout, код `0`.
- Отказ от подтверждения: `aborted` в stderr, код `1`.
- Ошибка (неизвестные `--src`/`--lb`/`--id`/`--where`/`--cnt`, несовместимые флаги,
  хранилище): `error: <текст>` в stderr, код `1`.

### Примеры

```bash
ds --db data.db delete --src CRM --lb junk_field --yes
# deleted 2 transaction(s)

# все ключи, у которых показатель is_test_account сейчас равен "true" -- со всеми их показателями
ds --db data.db archive --src CRM --where is_test_account=true --yes
# archived 6 transaction(s)

# всё, что загружено в БД раньше определённого дня (не путать с --dt-until -- это про created_at)
ds --db data.db archive --src CRM --created-until 1704067200 --yes
```

Метаданные показателя (запись в пуле `lbs`) при удалении не удаляются — только его транзакции;
показатель просто перестаёт встречаться в данных `ds get`. Чистка осиротевших записей пулов —
отдельная задача, см. [`../roadmap/optimization.md`](../roadmap/optimization.md). Полный
разбор — [`../../examples/05-delete-label/`](../../examples/05-delete-label/),
[`../../examples/07-archive-where/`](../../examples/07-archive-where/).

## `ds compact`

Находит транзакции, которые повторяют значение, уже действовавшее для той же пары
(показатель, ключ) — и потому не меняют результат `ds get` ни на один момент времени — и
переносит их в архив (по умолчанию) либо удаляет физически (`--hard`, как `ds delete`).
Реализация — `src/service/compact.py::find_duplicates` (вычисляет список `cnt`) +
уже существующие `txn_archive(cnts=...)`/`txn_delete(cnts=...)`.

**Правило.** История каждой пары (показатель, ключ) — активные и архивные транзакции вместе —
сортируется по `(dt, cnt)`. Первая запись всегда остаётся («опорная», не может быть дублем).
Каждая следующая запись — дубль, если её значение совпадает с последним **не-дублирующим**
значением перед ней (`DELETE`, то есть `val = null`, тоже значение — повторное `DELETE` подряд
тоже дубль). Пример: `X, X, Z` → вторая `X` — дубль (`Z` — нет, значение изменилось).

```
ds [--db PATH] compact --src NAME [--lb NAME]... [--id VALUE]... [--dt-from TS] [--dt-until TS] [--hard] [--yes]
```

| Аргумент | Обязателен | Значение |
|---|---|---|
| `--src NAME` | да | источник, как у `delete`/`archive`. |
| `--lb NAME` | нет | сузить сканирование до этих показателей (повторяемый); без него — все показатели источника. |
| `--id VALUE` | нет | сузить до этих ключей (повторяемый); без него — все ключи. |
| `--dt-from TS` / `--dt-until TS` | нет | ограничить анализ диапазоном бизнес-времени. **Первая запись, попавшая в диапазон** (по каждой паре показатель-ключ), становится опорной и никогда не помечается дублем — даже если бы оказалась дублем записи ДО начала диапазона. За пределы диапазона анализ сознательно не заглядывает — контекст не нужен, эта запись просто не рассматривается. |
| `--hard` | нет | физически удалить найденные дубли (обе таблицы), а не архивировать. |
| `--yes` | нет | не спрашивать подтверждение. |

Без `--yes` — сперва точный счётчик и до 5 примеров (`источник.показатель.ключ @ dt = значение`),
затем вопрос `Archive/Delete <N> duplicate transaction(s)? [y/N]`. В мягком режиме архивируются
только дубли, реально находящиеся сейчас в активной таблице (уже заархивированные дубли
`txn_archive` просто не затронет — они и так там); в `--hard` удаляются найденные дубли из
любой таблицы.

### Вывод

- Успех: `archived <N> duplicate transaction(s)` / `deleted <N> duplicate transaction(s)`, код `0`.
- Отказ от подтверждения: `aborted` в stderr, код `1`.
- Ошибка (`--src`/`--lb`/`--id` не найден, хранилище): `error: <текст>` в stderr, код `1`.

### Пример

```bash
ds --db data.db compact --src CRM --yes
# archived 1 duplicate transaction(s)
```

Полный разбор, включая `--dt-from` — [`../../examples/08-compact/`](../../examples/08-compact/).

## Коды возврата

| Код | Когда |
|---|---|
| `0` | команда выполнена |
| `1` | ошибка (конфиг, валидация, ввод-вывод, хранилище) — сообщение в stderr |
| `2` | ошибка разбора аргументов (`argparse`) |
